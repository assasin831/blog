# SmartMall AI 智能商城

SmartMall AI 是一个智能商城系统练习项目。它的目标不是只做几个静态页面，而是尽可能模拟真实电商平台的核心业务：用户浏览商品、搜索筛选、收藏评论、联系客服、加入购物车、余额支付、管理员运营后台，以及基于用户偏好和商品数据的 AI 导购推荐。

目前项目仍处在本地开发和持续打磨阶段，但已经形成了比较完整的业务闭环。

![SmartMall AI 首页](/images/smartmall/home.png)

## 项目定位

这个项目的定位是“商业级电商系统的学习型原型”。

它既要能体现前后端开发能力，也要能继续扩展数据库调优、高并发压测、缓存架构、推荐算法和 AI Agent 工程化能力。

核心目标包括：

- 搭建 Vue + Spring Boot + MySQL 的前后端分离架构。
- 实现真实电商用户的主要行为路径。
- 构建管理员端，让平台具备运营管理能力。
- 记录用户行为，为推荐系统提供数据基础。
- 使用 AI Agent 做商品导购，而不是简单闲聊。
- 预留 Redis 多级缓存、数据库索引优化和高并发压测空间。

## 技术栈

| 层级 | 技术 | 说明 |
| --- | --- | --- |
| 前端 | Vue、Vite、TypeScript、Pinia、Vue Router | 负责商城前台、用户中心、购物车、AI 助手和管理员端界面 |
| 后端 | Spring Boot、MyBatis Plus、Spring Security | 负责认证、商品、订单、购物车、钱包、客服、管理员接口 |
| 数据库 | MySQL | 存储用户、商品、订单、行为、钱包流水、评论和客服会话 |
| 缓存规划 | 本地缓存、Redis | 当前先做本地缓存和接口结构，后续升级多级缓存 |
| AI | Spring AI、千问模型接口、商城导购 Agent | 负责问题改写、商品筛选解释、多轮上下文和导购话术 |
| 测试规划 | JMeter / 压测脚本 | 后续用于 QPS、P95、P99、错误率和数据库压力测试 |

## 已完成功能

### 用户端

- 首页商品推荐、热卖榜、猜你喜欢。
- 商品分类、关键词搜索、智能排序。
- 商品详情页、规格选择、库存和服务信息。
- 加入购物车、修改数量、清空购物车。
- 收货人、手机号、地址填写。
- 余额充值和余额支付。
- 订单创建、历史订单查看。
- 收藏商品。
- 商品评论、评分和点赞。
- 商品详情页客服咨询。
- 用户中心查看余额、订单、收藏和账号信息。

### 管理员端

- 独立的后台管理入口。
- 数据看板。
- 商品管理。
- 订单管理。
- 用户管理。
- 客服工作台。

管理员端和用户端不能混在同一个界面里，这是电商系统很重要的边界。用户关心购买体验，管理员关心运营效率，两者的信息结构和交互逻辑应该不同。

### AI 导购助手

AI 助手当前已经从简单聊天，逐步演进为带约束的商城导购 Agent。

它需要做到：

- 理解预算、品类、用途、送礼对象和品牌偏好。
- 先检索商品库，再组织回答。
- 推荐商品时展示可购买商品卡片。
- 支持多轮追问，例如“有没有更便宜一点的”。
- 在没有匹配商品时明确说明没有，而不是编造商品。
- 对“你是谁”这类身份问题给出稳定回答。
- 对模型超时或异常进行本地推荐兜底。

## AI Agent 工作流

目前设计的导购流程是：

```text
用户输入
  -> 文本修复与基础清洗
  -> Prompt 改写
  -> 意图识别
  -> 预算 / 品类 / 品牌 / 场景约束抽取
  -> 读取多轮记忆
  -> 商品库检索与排序
  -> 判断是否存在严格匹配商品
  -> 生成导购回答
  -> 返回商品卡片、购买建议、追问问题
  -> 写入记忆并在对话过长时压缩上下文
```

这个流程的重点是“先查库，再回答”。AI 不能绕开商品库直接生成，因为商城导购推荐的商品必须真实存在、价格正确、库存可用。

## Q / K / V 记忆机制

多轮导购最容易出错的地方是上下文丢失。比如：

1. 用户先问：`有没有 400 元左右的手机推荐一下？`
2. 系统推荐：`Nova Mini 4G 实用手机，399 元。`
3. 用户追问：`有没有比这个手机更便宜的？`

第三句里的“这个手机”必须指向上一轮的 `Nova Mini 4G`，而不是重新随机推荐。

因此对话记忆按 Q / K / V 思路拆开：

| 结构 | 含义 | 在项目中的作用 |
| --- | --- | --- |
| Q | 当前问题 | 判断用户本轮到底想买什么、比较什么、追问什么 |
| K | 检索关键词 | 品类、预算、品牌、上一轮商品、价格约束 |
| V | 可复用结果 | 上一轮推荐商品、价格、品类、总结出的偏好 |

当用户说“更便宜一点”时，系统会读取上一轮价格，并追加严格条件：新商品价格必须低于上一轮商品价格，品类仍保持一致。

## 商品推荐与行为分值

后续首页推荐不应该只靠固定推荐分，而是要根据用户行为逐渐个性化。

目前规划的行为数据包括：

| 行为 | 说明 | 推荐意义 |
| --- | --- | --- |
| 浏览 | 用户看过某个商品 | 表示轻度兴趣 |
| 收藏 | 用户收藏商品 | 表示较明确兴趣 |
| 加购 | 用户加入购物车 | 表示购买意向强 |
| 评价 | 用户购买后留下评价 | 表示真实使用反馈 |
| 购买 | 用户完成订单 | 表示强偏好和真实成交 |

推荐逻辑可以从简单分值开始，再逐步加入协同过滤：

- 同一个用户经常浏览和购买的品类，提高该品类在首页的展示权重。
- 相似用户都购买过的商品，可以推荐给当前用户。
- 同一商品被收藏、加购、购买次数越多，热度越高。
- AI 导购可以把用户偏好写入记忆，下一次推荐时作为补充信号。

## 数据库三层架构思想

这个项目后续要做数据库调优和高并发测试，所以数据库设计不能只停留在“能查出来”。当前把数据架构拆成三层理解。

### 第一层：核心业务表

这一层负责数据真实可靠。

典型表包括：

- `mall_user`：用户、角色、状态、余额。
- `mall_category`：商品分类。
- `mall_product`：商品主数据、价格、库存、销量、推荐分。
- `mall_cart_item`：购物车。
- `mall_order`、`mall_order_item`：订单与订单明细。
- `mall_favorite`：收藏。
- `mall_review`：评价。
- `mall_wallet_transaction`：余额充值和支付流水。
- `mall_behavior`：浏览、收藏、加购、购买等用户行为。
- `mall_service_conversation`、`mall_service_message`：客服会话。
- Agent 记忆相关结构：用户偏好、最近一轮导购上下文、摘要记忆。

### 第二层：查询与索引层

这一层解决高频读写场景。

后续重点关注：

- 商品列表分页是否走索引。
- 分类筛选和价格排序是否稳定。
- 搜索关键词是否能排除弱相关商品。
- 用户订单、收藏、行为记录是否按用户和时间建立索引。
- 钱包流水是否能快速追踪交易历史。
- 管理端订单和商品状态查询是否能承受运营高频操作。

### 第三层：缓存与推荐层

这一层面向高并发和个性化推荐。

规划中的缓存路径是：

```text
浏览器请求
  -> 前端状态缓存
  -> 后端本地缓存
  -> Redis 热点缓存
  -> MySQL 回源
```

适合缓存的数据：

- 商品分类。
- 首页热卖榜。
- 商品详情。
- 首页猜你喜欢候选集。
- AI 导购的商品候选结果。
- 管理端低频变化的统计数据。

缓存失效策略后续要结合后台管理操作来做：商品价格、库存、状态变化后，需要删除或刷新对应商品详情、列表和推荐缓存。

## 搜索相关性优化

之前搜索“手机”时，商品列表里会出现智能家居商品，因为它们的描述里有“手机远程控制”。

这个问题说明搜索不能只靠全文包含，还要做权重区分：

- 商品名称命中“手机”权重最高。
- 商品分类命中“手机数码”权重较高。
- 副标题命中有一定权重。
- 描述里出现“手机远程控制”只能作为弱信号。
- 如果用户明确要“手机”，非手机品类需要降权甚至过滤。

优化后，搜索“手机”会优先出现真正的手机商品。

## UI 打磨方向

当前 UI 主要参考真实电商平台的信息结构：

- 京东式顶部搜索和购物车入口。
- 淘宝式多类目、推荐流和商品卡片。
- 亚马逊式商品详情信息块和购买决策信息。
- 管理端单独使用后台式侧边栏和运营看板。

前台的重点是让用户快速买东西；后台的重点是让管理员快速处理商品、订单、用户和客服。

## 高并发与调优计划

后续要做的不是只跑通功能，而是验证系统在压力下的表现。

计划压测的接口包括：

- 商品列表。
- 商品详情。
- 搜索接口。
- 加入购物车。
- 创建订单。
- 余额支付。
- AI 导购接口。
- 管理端订单列表。

关注指标：

- QPS。
- 平均响应时间。
- P95 / P99 响应时间。
- 错误率。
- 数据库连接池使用情况。
- 慢 SQL。
- Redis 命中率。
- AI 接口超时比例。

对 AI 导购接口会单独设计降级：模型慢的时候，先返回后端本地商品推荐；模型恢复后，再继续优化导购话术。

## 下一阶段计划

1. 引入 Redis，完成分类、商品详情、首页推荐的多级缓存。
2. 为商品、订单、行为、钱包流水补充更完整的索引设计。
3. 用 JMeter 做第一轮并发压测，输出 QPS、P95、P99 和瓶颈分析。
4. 把推荐算法从固定分值升级为用户行为分 + 相似商品 / 相似用户。
5. 继续强化 AI Agent：品牌识别、严格条件过滤、多轮压缩记忆、工具调用链路。
6. 完善管理员端的商品上下架、订单状态流转和客服处理体验。
