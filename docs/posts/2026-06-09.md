# 6.9 学习：SmartMall AI RabbitMQ 可观测性与秒杀幂等补偿优化

6.8 已经把 SmartMall AI 的 RabbitMQ / outbox 链路推进到了比较稳定的阶段：用户画像迁移到消费者、outbox 并行投递、订单事件 5000 压测、管理员后台监控页和秒杀预留链路都已经完成。

今天继续按照昨天留下来的后续计划往下做，重点变成两个方向：

1. 让消息链路更可观测：不能只看全局 published / consumed，要知道是哪一个 routing key 在积压，也要能看到 RabbitMQ 队列里的 ready / unacked。
2. 让秒杀链路更接近真实业务：补 requestId 幂等、用户重复购买限制，以及异步建单失败后的 Redis 库存补偿。

## 为什么要按 routing key 统计

昨天的监控已经能看到全局指标：

```text
published
publishFailures
consumed
consumeFailures
outbox pending
outbox failed
```

但真实排障时，只看全局是不够的。比如全局 pending 变高时，它可能来自三条完全不同的链路：

```text
behavior.recorded           用户行为画像
order.created               订单创建后续事件
seckill.order.requested     秒杀异步建单事件
```

如果不拆开看，就很难判断到底是用户画像消费者慢、订单事件慢，还是秒杀建单慢。

所以今天在 `MessagingMonitorService` 里新增了按 routing key 的计数器，每个 routing key 单独记录：

```text
published
publishFailures
skipped
consumed
consumeFailures
avgPublishLatencyMillis
avgConsumeLatencyMillis
```

后台新增接口：

```text
GET /api/admin/messaging/routes
```

管理员后台也增加了 Routing Key Stats 表格，这样压测时可以直接看到每条业务事件线的发布、消费和失败情况。

## 接入 RabbitMQ Management API

昨天管理员后台能看 outbox，但还不能直接看到 RabbitMQ 队列深度。

今天增加了一个 Management API 轮询服务，配置项是：

```text
RABBITMQ_MANAGEMENT_ENABLED=true
RABBITMQ_MANAGEMENT_BASE_URL=http://localhost:15672
RABBITMQ_MANAGEMENT_USERNAME=smartmall
RABBITMQ_MANAGEMENT_PASSWORD=smartmall
```

后台新增接口：

```text
GET /api/admin/messaging/queues
```

它会拉取这些队列：

```text
smartmall.behavior.events
smartmall.order.events
smartmall.seckill.order.events
smartmall.events.dlq
```

重点看三个值：

```text
ready      队列中等待消费的消息
unacked    已投递给消费者但还没有 ack 的消息
consumers  当前消费者数量
```

这一步非常重要。因为 outbox pending 为 0 只说明消息已经投递到 RabbitMQ，不代表消费者已经处理完。队列 ready / unacked 才能说明 RabbitMQ 里面有没有积压。

## 秒杀 requestId 幂等

秒杀链路昨天已经有 Redis Lua 扣库存：

```text
POST /api/seckill/orders
  -> Redis Lua 原子扣库存
  -> 写 seckill.order.requested outbox
  -> RabbitMQ 消费者异步创建订单
```

但还有一个真实业务里很危险的问题：用户重复点击按钮，或者浏览器重发请求，可能导致库存被扣多次。

今天给秒杀请求增加了 `requestId`：

```json
{
  "requestId": "seckill-xxx",
  "productId": 1,
  "quantity": 1
}
```

后端会用 Redis 保存：

```text
smartmall:seckill:request:{requestId}
```

同一个 `requestId` 再次进入时，不再扣库存，而是直接返回：

```text
DUPLICATE_REQUEST
```

这相当于给浏览器重复提交、网络抖动重试、前端按钮连点加了一层保护。

## 用户重复购买限制

除了 requestId，还需要限制同一个用户重复抢同一个商品。

今天新增 Redis key：

```text
smartmall:seckill:user-product:{userId}:{productId}
```

同一个用户第一次抢某个商品时写入成功；如果同一用户换一个 requestId 再抢同一个商品，就返回：

```text
ALREADY_REQUESTED
```

这样可以防止同一个账号反复占库存。后续如果要做真实秒杀活动，可以继续把这个限制扩展成：

```text
每人每活动限购 1 件
每人每 SKU 限购 N 件
按活动 ID + 用户 ID + 商品 ID 组合限购
```

## 异步失败后的库存补偿

秒杀请求线程只扣 Redis 库存，然后把建单事件交给 RabbitMQ。

这就带来一个一致性问题：

```text
Redis 库存已经扣了
RabbitMQ 消费者异步创建订单失败
```

如果不补偿，Redis 库存就会少一件，但订单并没有创建成功。

今天给消费者补了失败补偿逻辑：

```text
smartmall:seckill:compensated:{requestId}
```

补偿时先写这个 key，保证同一个失败事件只补偿一次。然后：

```text
Redis stock + quantity
删除 user-product 限购锁
把 request 状态标记为 FAILED
```

这样即使消费者异常，也不会让 Redis 库存一直少下去。

## 管理员后台新增观测块

今天后台消息队列页继续增强，现在能看到：

```text
RabbitMQ Queue Depth
Routing Key Stats
Outbox 策略
最近消息事件
Outbox 明细
```

这次新增的两个表很关键：

```text
Queue Depth:
queue / total / ready / unacked / consumers / state

Routing Key Stats:
routing key / total / published / consumed / failures / avg latency
```

有了这两个表，后面压测就能快速判断：

- outbox 有没有积压。
- RabbitMQ 队列有没有积压。
- 哪个 routing key 消费慢。
- 是否有 ready 消息一直堆着。
- 是否有 unacked 消息卡在消费者里。

## 三条链路压测

今天本地启动了 MySQL、Redis、RabbitMQ，并用昨天推荐的 RabbitMQ 参数继续压测：

```text
SMARTMALL_MESSAGING_ENABLED=true
RABBITMQ_MANAGEMENT_ENABLED=true
RABBITMQ_PREFETCH=100
RABBITMQ_CONSUMER_CONCURRENCY=4
RABBITMQ_CONSUMER_MAX_CONCURRENCY=16
SMARTMALL_MESSAGING_OUTBOX_BATCH_SIZE=1000
SMARTMALL_MESSAGING_OUTBOX_DISPATCH_INTERVAL_MILLIS=200
SMARTMALL_MESSAGING_OUTBOX_DISPATCH_PARALLELISM=8
```

这次压了三条链路：

| 链路 | 总量 | 并发 | 成功 | 失败 | RPS | p95 | p99 | outbox |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 行为事件 | 1000 | 100 | 1000 | 0 | 579.55 | 274.91ms | 387.27ms | pending 0 |
| 订单事件 | 1000 | 100 | 1000 | 0 | 554.15 | 277.84ms | 330.61ms | pending 0 |
| 秒杀请求 | 1000 | 100 | 1000 | 0 | 1126.97 | 123.73ms | 144.22ms | 瞬时 pending 74，最终归 0 |

秒杀链路的 p95 更低，是因为请求线程只做：

```text
requestId 幂等检查
用户商品限购检查
Redis Lua 扣库存
outbox 入库
```

真正的订单创建、BUY 行为事件和推荐缓存刷新都交给 RabbitMQ 消费者异步做。

最后又手动测了一次同用户同商品的秒杀请求：

## 今天的理解

今天这轮优化让我更清楚地看到：消息队列不是“加一个 RabbitMQ”就结束。

一个真实一点的电商系统至少要继续问：

- 请求是否足够轻。
- 事件有没有可靠落库。
- outbox 有没有积压。
- RabbitMQ ready / unacked 是否稳定。
- 每个 routing key 是否独立可观测。
- 异步失败后有没有补偿。
- 重复请求会不会造成重复扣库存。
- 用户重复购买有没有被业务层限制。

今天把这些问题往前推进了一步。SmartMall AI 的消息链路现在不只是能跑，而是开始具备可解释、可压测、可补偿、可排障的形状。
