# 6.8 学习：SmartMall AI RabbitMQ/outbox 深度优化与 5000 并发压测闭环

6.7 已经把 SmartMall AI 的 RabbitMQ 链路推进到 outbox 模式，也补了行为事件压测脚本。

今天继续按昨天的计划往下做，重点不再是“接入消息队列”，而是把消息队列真正放到高并发电商系统的工作方式里：请求线程尽量轻，异步链路可恢复，管理员能看到积压，压测结果能说清楚。

## 今天要解决的问题

昨天留下来的计划主要有五件事：

1. 把用户画像重建迁移到 RabbitMQ 消费者，降低行为接口 p95。
2. 增加订单事件压测，观察 `order.created` 在高并发下的 outbox 积压。
3. 在管理员后台增加 RabbitMQ / outbox 可视化页面。
4. 做 RabbitMQ 开启/关闭、不同 prefetch、不同消费者并发的对比报告。
5. 为秒杀模块预留 Redis Lua 扣库存 + RabbitMQ 异步建单链路。

这几个问题本质上都指向同一个方向：让 SmartMall AI 从“能跑的 Demo”继续往“有高并发意识的商业级系统”靠近。

## 用户画像迁移到消费者

之前用户点击、收藏、加购、购买商品时，请求线程里会同步做几件事：

```text
写 mall_user_behavior
更新用户类目偏好分值
清理推荐缓存
写 outbox
```

这里的问题是，用户画像更新虽然重要，但它不应该拖慢用户行为接口。

今天把这部分逻辑继续往 RabbitMQ 消费者侧迁移：

```text
POST /api/behaviors
  -> 写用户行为
  -> 写 behavior.recorded outbox
  -> 快速返回

RabbitMQ consumer
  -> 消费 behavior.recorded
  -> 增量更新用户类目偏好
  -> 清理用户推荐缓存
```

这样行为接口只负责把事实记录下来，画像更新交给异步链路处理。

这一步带来的收益很直接：请求线程少做数据库写入和推荐相关逻辑，高并发下 p95 明显下降。

## Outbox 并行投递优化

6.7 的 outbox 已经解决了“业务事件不丢”的问题，但今天在 5000 条订单压测时又暴露出一个新瓶颈：

```text
请求都成功了
RabbitMQ 没有失败
但是 outbox 在观察窗口里有明显积压
```

第一轮 5000 订单事件压测后，15 秒观察窗口里 outbox 还有 7515 条 pending。它不是错误，而是后台投递器吞吐不够。

所以今天把 outbox 投递器从单线程批处理升级成可配置并行投递：

```text
SMARTMALL_MESSAGING_OUTBOX_BATCH_SIZE=1000
SMARTMALL_MESSAGING_OUTBOX_DISPATCH_INTERVAL_MILLIS=200
SMARTMALL_MESSAGING_OUTBOX_DISPATCH_PARALLELISM=8
```

新的链路是：

```text
调度器扫描 PENDING outbox
  -> 一次最多取 1000 条
  -> 交给 8 路并行投递线程
  -> RabbitMQ 发布成功后更新 PUBLISHED
  -> 失败则按 attempts / nextRetryAt 重试
```

这一步的意义是：请求侧负责削峰，outbox 侧负责尽快把积压送进 RabbitMQ。

## 订单事件 5000 压测

今天新增并完善了订单事件压测脚本：

```bash
node scripts/load-order-messaging.mjs \
  --baseUrl http://localhost:8080 \
  --total 5000 \
  --concurrency 100 \
  --settleMs 15000 \
  --output docs/perf-results/order-on-prefetch100-c4-p8.json
```

这个脚本会自动完成：

1. 登录普通用户和管理员。
2. 拉取可用商品。
3. 并发调用下单接口。
4. 等待 outbox 和 RabbitMQ 消费稳定。
5. 拉取消息统计、outbox 统计和最近事件。
6. 把最终 JSON 结果写入 `docs/perf-results/`。

最终推荐档结果：

| 场景 | 总量 | 并发 | 成功 | 失败 | RPS | p95 | p99 | outbox pending | outbox failed |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 订单事件推荐档 | 5000 | 100 | 5000 | 0 | 542.97 | 317.81ms | 382.06ms | 0 | 0 |

这说明在当前本地环境下，订单创建、库存扣减、`order.created`、`behavior.recorded` 和 outbox 投递都能在 5000 请求压力下保持稳定。

## 行为接口 5000 压测

行为接口是今天优化的重点，因为用户点击、收藏、加购这类行为会非常频繁。

推荐档配置：

```text
SMARTMALL_MESSAGING_ENABLED=true
RABBITMQ_PREFETCH=100
RABBITMQ_CONSUMER_CONCURRENCY=4
RABBITMQ_CONSUMER_MAX_CONCURRENCY=16
SMARTMALL_MESSAGING_OUTBOX_BATCH_SIZE=1000
SMARTMALL_MESSAGING_OUTBOX_DISPATCH_INTERVAL_MILLIS=200
SMARTMALL_MESSAGING_OUTBOX_DISPATCH_PARALLELISM=8
```

压测结果：

| 场景 | 总量 | 并发 | 成功 | 失败 | RPS | p95 | p99 | outbox pending |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 行为接口推荐档 | 5000 | 100 | 5000 | 0 | 1290.20 | 118.72ms | 159.97ms | 0 |

这次最大的变化是 p95 从之前几百毫秒甚至上秒级，降到了 118.72ms。

这说明把画像更新和推荐相关逻辑从请求线程迁移到消费者，是非常有效的。

## RabbitMQ 参数矩阵

今天还做了 RabbitMQ 参数矩阵，不只看一个配置。

对比了四种模式：

| 配置 | MQ | prefetch | 消费者 | outbox 并行 | 成功 | 失败 | RPS | p95 | p99 | outbox pending |
| --- | --- | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| MQ 关闭基线 | false | 0 | 0/0 | 4 | 5000 | 0 | 1302.71 | 137.15ms | 180.66ms | 0 |
| MQ 开启低消费者 | true | 50 | 2/8 | 4 | 5000 | 0 | 938.13 | 165.09ms | 228.48ms | 1855 |
| MQ 开启推荐档 | true | 100 | 4/16 | 8 | 5000 | 0 | 1290.20 | 118.72ms | 159.97ms | 0 |
| MQ 开启高吞吐档 | true | 200 | 8/24 | 12 | 5000 | 0 | 876.22 | 207.50ms | 259.26ms | 0 |

这里有一个很重要的结论：

高吞吐档不是最优档。

消费者并发和 outbox 并行数开得太高以后，请求线程、消费者线程和 outbox 投递线程会一起争抢 MySQL 连接池，反而让接口 p95 变差。

所以今天得到的推荐配置不是“全部拉满”，而是：

```text
prefetch=100
consumer=4/16
outbox batch=1000
dispatch interval=200ms
outbox parallelism=8
```

这更像真实系统调优：不是追求参数最大，而是找请求延迟、后台积压和数据库连接之间的平衡点。

## 管理员后台消息队列可视化

今天把管理员后台的消息队列页面继续完善了。

现在管理员可以看到：

```text
MQ 是否开启
exchange
已发布数量
发布失败数量
已消费数量
消费失败数量
outbox pending
outbox failed
batch size
outbox 并行投递数
最大重试次数
重试退避基数
最近消息事件
最近 outbox 明细
```

这个页面很重要，因为高并发系统不能只靠“接口没报错”判断状态。

例如今天第一轮订单 5000 压测，HTTP 层大部分是正常的，但 outbox 观察窗口内有积压；如果没有监控页，就很难发现后台投递器才是真正瓶颈。

## 登录态和后台细节修复

压测以外，今天还修了一个比较真实的后台问题。

管理员登录后，前端原本还会去加载用户购物车：

```text
管理员登录
  -> 拉取购物车
  -> 管理员角色没有购物车权限
  -> 403
```

这个问题会干扰后台页面初始化。

今天改成：

```text
普通用户登录后加载购物车
管理员登录后直接进入后台
```

同时又补了一个内存级 token 会话层。原因是 axios 拦截器之前只从 `localStorage` 取 token，在某些受限浏览器上下文里，页面能进后台，但请求不一定能拿到 token。

现在登录后 token 会同时保存在：

```text
Pinia state
memory token
localStorage
```

axios 请求优先读 memory token，再读 localStorage。这样当前页面的后台 API 会更稳定。

## 秒杀链路预留

秒杀模块今天继续保持预留链路：

```text
POST /api/seckill/orders
  -> Redis Lua 原子扣库存
  -> 写 seckill.order.requested outbox
  -> RabbitMQ 消费者异步创建订单
  -> 发出 order.created
  -> 发出 BUY 行为事件
```

这条链路现在还不是最终生产版本，但方向已经清楚：

- Redis Lua 负责高并发库存原子扣减。
- RabbitMQ 负责削峰异步建单。
- outbox 保证请求进入队列前的事件可靠性。
- 订单创建失败后还需要补偿 Redis 库存。

后续要继续补的是幂等、重复请求保护、失败补偿和真实秒杀活动配置。

## 今天的收获

今天最大的收获是：消息队列调优不是“加 RabbitMQ 就结束了”。

真正要看的东西包括：

- 请求线程有没有变轻。
- outbox 有没有积压。
- RabbitMQ 发布和消费有没有失败。
- 消费者并发是否和数据库连接池打架。
- 订单号、库存扣减、用户画像更新有没有锁竞争。
- 管理员能不能看到消息状态。
- 压测数据能不能落盘，形成可复盘报告。

这次 SmartMall AI 的异步链路已经更像一个真正的电商系统了：请求、事件、缓存、画像、订单、秒杀预留、后台监控都开始连接成一条完整链路。
