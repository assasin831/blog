# 6.7 学习：SmartMall AI 消息队列 outbox 与 RabbitMQ 压测优化

6.6 给 SmartMall AI 接入了 RabbitMQ，完成了行为事件、订单事件、交换机、队列、死信队列和基础观测接口。

今天继续沿着 6.6 的后续计划往下做，重点不是再加一个功能页，而是把消息队列从“能发出去”往“更可靠、更可观测、更适合压测”推进。

## 今天的核心问题

6.6 的事件发布逻辑是：

```text
数据库事务提交
  -> afterCommit
  -> 发布 RabbitMQ 消息
```

这个方案已经比事务中途直接发消息安全，但仍然有一个极端风险：

```text
数据库事务提交成功
应用在 afterCommit 发布前宕机
消息没有发出去
```

如果这是订单通知、推荐刷新、运营统计或后续秒杀订单创建，就会出现“数据库有记录，但异步链路漏了一条事件”的问题。

所以今天把 RabbitMQ 投递升级成 outbox 模式。

## Outbox 可靠投递

今天新增了 `mall_message_outbox` 表，用来保存待发布的业务事件。

核心字段包括：

```text
event_id
routing_key
event_type
payload_json
status
attempts
next_retry_at
last_error
created_at
updated_at
published_at
```

现在事件链路变成：

```text
业务事务内
  -> 写用户行为 / 订单数据
  -> 写 mall_message_outbox
事务提交后
  -> 立即尝试投递 RabbitMQ
投递失败
  -> 保留 PENDING / FAILED 状态
  -> 调度器批量重试
```

这样就算 RabbitMQ 短暂不可用，业务事件也不会直接丢掉。

## 为什么 outbox 很重要

电商系统里有很多“主业务必须成功，后续任务可以稍后完成”的场景：

- 下单成功后异步刷新推荐。
- 购买行为进入用户画像。
- 订单创建后通知客服/运营。
- 秒杀请求削峰后异步创建订单。
- 用户行为进入统计和推荐训练。

这些任务不应该阻塞用户主请求太久，但也不能随便丢。outbox 就是在数据库和消息队列之间加了一层可靠缓冲。

今天的设计相当于把消息状态也纳入 MySQL 可追踪范围。

## RabbitMQ 参数优化

这次也把 RabbitMQ 消费参数做成环境变量：

```text
RABBITMQ_CONSUMER_CONCURRENCY=2
RABBITMQ_CONSUMER_MAX_CONCURRENCY=8
RABBITMQ_PREFETCH=50
```

含义是：

- `concurrency`：初始消费者线程数。
- `max-concurrency`：压力上来后允许扩展到的最大消费者数。
- `prefetch`：单个消费者一次最多预取多少条消息。

另外，失败处理也做了配置：

```text
default-requeue-rejected=false
retry.max-attempts=3
retry.initial-interval=300ms
retry.multiplier=2
```

这样消费者失败时不会无限 requeue，把队列拖死；超过重试后可以进入死信队列。

## Outbox 调度参数

outbox 自己也有一组参数：

```text
SMARTMALL_MESSAGING_OUTBOX_BATCH_SIZE=50
SMARTMALL_MESSAGING_OUTBOX_MAX_ATTEMPTS=5
SMARTMALL_MESSAGING_OUTBOX_RETRY_BASE_MILLIS=1000
SMARTMALL_MESSAGING_OUTBOX_DISPATCH_INTERVAL_MILLIS=5000
```

这几个参数控制：

- 每次最多投递多少条 outbox 事件。
- 单条事件最多重试多少次。
- 失败后基础重试间隔。
- 调度器多久扫描一次待投递消息。

也就是说，后续压测时可以不用改代码，直接调环境变量观察吞吐和延迟变化。

## 管理员观测接口

6.6 只有消息发布和消费统计。今天继续补 outbox 观测：

```http
GET /api/admin/messaging/outbox/stats
GET /api/admin/messaging/outbox?status=FAILED&limit=30
POST /api/admin/messaging/outbox/retry-failed?limit=50
```

现在管理员可以看到：

```text
pending
published
failed
batchSize
maxAttempts
retryBaseMillis
```

也可以查看最近 outbox 记录：

```text
id
eventId
routingKey
eventType
status
attempts
nextRetryAt
lastError
payloadBytes
```

如果某些事件失败，可以手动重新放回待投递状态。

## 消息压测脚本

今天新增了专门压测消息队列链路的脚本：

```bash
node scripts/load-messaging.mjs --baseUrl http://localhost:8080 --total 300 --concurrency 50 --settleMs 3000
```

它会自动：

1. 登录普通用户。
2. 登录管理员。
3. 拉取一批商品 ID。
4. 并发调用 `POST /api/behaviors`。
5. 等待 RabbitMQ 消费稳定。
6. 拉取消息发布/消费统计。
7. 拉取 outbox 统计和最近事件。

相比只看接口响应，这个脚本能同时回答：

- HTTP 接口有没有失败？
- RabbitMQ 发布是否成功？
- 消费者有没有消费完？
- outbox 有没有 pending 或 failed 堆积？

## 单条链路验证

启动 RabbitMQ 后，先跑了一次观测脚本：

```bash
node scripts/observe-messaging.mjs --baseUrl http://127.0.0.1:8080 --limit 5 --waitMs 1500
```

结果：

```text
enabled: true
published: 1
publishFailures: 0
consumed: 1
consumeFailures: 0
outbox pending: 0
outbox published: 1
outbox failed: 0
```

最近事件里可以看到：

```text
publish success behavior.recorded latencyMillis: 9
consume success behavior.recorded latencyMillis: 534
```

第一条消费延迟偏高，是因为消费者会触发推荐缓存预热，后面压测时消费延迟下降到几毫秒级。

## 300 条行为事件压测

今天跑了一轮行为事件压测：

```text
total: 300
concurrency: 50
actionType: VIEW
```

接口结果：

```text
ok: 300
failed: 0
errorRate: 0
RPS: 75.23
p50: 617.29 ms
p95: 853.02 ms
p99: 877.19 ms
```

消息队列结果：

```text
published: 301
publishFailures: 0
consumed: 301
consumeFailures: 0
outbox pending: 0
outbox published: 301
outbox failed: 0
```

这里的 `301` 是因为压测前还跑了一次单条观测。

这轮说明 RabbitMQ 和 outbox 链路是通的：没有发布失败，没有消费失败，没有 pending 积压，也没有 failed 消息。

## 为什么接口 p95 还偏高

这轮行为事件接口的 p95 大约 853ms，看起来不低，但原因也很清楚：

当前 `POST /api/behaviors` 仍然同步做了几件事：

```text
写 mall_user_behavior
更新用户类目偏好
清理用户推荐缓存
写 outbox
事务提交
```

也就是说，RabbitMQ 已经承担了后续推荐预热，但用户画像增量更新还在主请求里。

这恰好给下一步优化指出了方向：可以继续把“画像完整重建、运营统计、通知、部分推荐刷新”迁移到消费者里，让行为接口更轻。

## 今天的收获

今天最大的收获是，消息队列优化不能只看“吞吐量更高”。

真正的工程问题是：

- 消息会不会丢？
- 失败能不能重试？
- 队列堆积能不能看到？
- 消费者失败会不会无限 requeue？
- 管理员能不能查到 failed 消息？
- 压测时能不能同时看到 HTTP 和 MQ 两边的数据？

6.6 是把 RabbitMQ 接进系统，6.7 则是让 RabbitMQ 变得更像一个生产系统里的异步链路。
