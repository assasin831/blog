# 6.6 学习：SmartMall AI 引入 RabbitMQ 事件总线与异步削峰

6.5 做完缓存热点观测和 Agent 审计之后，我继续思考一个问题：如果后面 SmartMall AI 要往真实电商系统靠，不能所有事情都同步堆在一次请求里。

商品查询可以靠 Caffeine + Redis + MySQL 三级缓存来扛读压力，但用户行为、订单后的推荐刷新、运营统计、通知、日志沉淀这些任务，更适合通过消息队列异步化。今天就把 SmartMall AI 的第一版消息队列架构接上了。

## 为什么选择 RabbitMQ

一开始考虑过继续用 Redis Stream，因为项目里已经有 Redis。但 Redis 现在承担的是缓存、热点 key、空值防穿透、TTL 抖动和推荐结果缓存。如果再把大量业务事件也压到 Redis 上，缓存层和消息层会互相影响。

所以今天选择 RabbitMQ 作为当前阶段的业务消息队列：

- RabbitMQ 更适合订单、行为、推荐刷新这类可靠业务事件。
- 它天然支持交换机、路由键、ACK、重试、死信队列和管理界面。
- Spring Boot 对 RabbitMQ 的集成成熟，接入成本比自己维护 Redis Stream 消费组更低。
- Kafka 更适合后续海量埋点、行为日志流、离线推荐训练和数据分析，但现在引入 Kafka 运维成本偏高。

所以当前分工是：

```text
Redis：缓存、热点 key、短期状态、推荐结果缓存
RabbitMQ：业务事件、异步削峰、推荐缓存预热、失败消息进入 DLQ
Kafka：后续如果做大规模行为日志和离线推荐，再考虑引入
```

## 今天做了什么

今天主要完成了六块：

1. 后端引入 `spring-boot-starter-amqp`。
2. 新增 RabbitMQ exchange、queue、routing key 和 DLQ 配置。
3. 新增用户行为事件 `behavior.recorded` 和订单创建事件 `order.created`。
4. 在事务提交后发布事件，避免数据库回滚但消息已经发出的错位。
5. 增加 no-op publisher，本地没启动 RabbitMQ 时系统仍然能正常运行。
6. 增加管理员消息观测接口和 `observe-messaging.mjs` 脚本。

## 事件拓扑

这次新增的拓扑如下：

```text
BehaviorService / OrderService
  -> TransactionAfterCommit
  -> RabbitMQ topic exchange: smartmall.events
      -> behavior.recorded -> smartmall.behavior.events
      -> order.created     -> smartmall.order.events
      -> consume failed    -> smartmall.events.dlx -> smartmall.events.dlq
```

也就是说，业务服务不会直接在请求线程里做所有后续计算，而是把事件发布出去，让消费者异步处理。

## 主链路仍然保持同步

今天没有把核心业务完全异步化，这是一个有意的选择。

例如下单流程里，库存扣减、订单创建、订单明细写入、购买行为记录仍然是同步执行。这样用户提交订单后，核心数据已经确定落库，不会因为 MQ 暂时不可用导致订单状态不确定。

RabbitMQ 负责的是后续异步任务：

- 行为事件消费后预热用户个性化推荐缓存。
- 订单事件消费后重建用户推荐画像。
- 订单创建后清理首页推荐缓存。
- 失败消息进入死信队列，后续可以做人工排查或补偿消费。

这相当于先把系统拆成：

```text
强一致主链路：下单、库存、订单、用户行为落库
最终一致异步链路：推荐刷新、缓存预热、运营统计、后续通知
```

这个分层比直接把所有写操作都丢进消息队列更稳。

## 事务提交后再发布

如果在事务中间就发 MQ，会出现一个危险情况：

```text
消息已经发出
数据库事务最后回滚
消费者拿到一个并不存在的订单或行为
```

所以今天新增了 `TransactionAfterCommit` 工具，只有数据库事务提交成功之后，才真正发布 RabbitMQ 事件。

这样消息队列看到的事件，至少代表当前数据库主链路已经成功完成。

## 本地降级模式

本地开发不应该被 RabbitMQ 卡住，所以今天做了可开关设计：

```yaml
smartmall:
  messaging:
    enabled: ${SMARTMALL_MESSAGING_ENABLED:false}
```

默认关闭时使用 no-op publisher。它不会真的连接 RabbitMQ，而是把事件记录成 `skipped`，方便管理员接口看到“这次事件本来会发布，但当前 MQ 未开启”。

生产环境可以在 `.env.prod` 中打开：

```bash
SMARTMALL_MESSAGING_ENABLED=true
RABBITMQ_HOST=rabbitmq
RABBITMQ_PORT=5672
RABBITMQ_USERNAME=smartmall
RABBITMQ_PASSWORD=change_me_rabbit
```

`docker-compose.prod.yml` 也补上了 RabbitMQ 服务，和 MySQL、Redis、后端、前端一起启动。

## 补齐加购行为

今天还发现一个小细节：推荐规则里有 `CART +6`，但购物车加购之前没有真正记录用户行为。

所以这次把 `CartService.addItem` 也接入了 `BehaviorService.record`。现在用户画像链路更完整：

```text
VIEW +1
FAVORITE +5
CART +6
REVIEW +4
BUY +12
```

这对首页推荐和 AI 导购都有帮助。用户不是只有购买才表达偏好，浏览、收藏、加购其实都是很重要的信号。

## 管理员观测接口

消息队列不能只停留在“代码接上了”，必须能看状态。今天新增了两个管理员接口：

```http
GET /api/admin/messaging/stats
GET /api/admin/messaging/events?limit=30
```

可以看到：

```text
enabled
exchange
behaviorQueue
orderQueue
deadLetterQueue
published
publishFailures
skipped
consumed
consumeFailures
recentEventSize
```

最近事件里还会记录：

```text
phase
status
routingKey
payloadType
userId
productId
orderId
latencyMillis
message
```

以后如果 RabbitMQ 消费慢、失败变多、DLQ 堆积，就能从这里开始查。

## 新增观察脚本

今天新增：

```bash
node scripts/observe-messaging.mjs --baseUrl http://localhost:8080 --limit 10
```

脚本会自动：

1. 登录普通用户。
2. 登录管理员。
3. 找一个商品。
4. 发送一次用户行为事件。
5. 等待消费者处理。
6. 拉取消息队列统计和最近事件。

本地默认 MQ 关闭，所以观察结果中会看到 `skipped`：

```text
enabled: false
published: 0
publishFailures: 0
skipped: 2
consumed: 0
consumeFailures: 0
recentEventSize: 2
```

这说明事件链路已经走到了发布器，只是当前环境没有启用 RabbitMQ。等后续打开 MQ 后，同一个脚本就能看到 `published` 和 `consumed` 增加。

## 验证结果

后端编译通过：

```bash
mvn -DskipTests package
```

本地启动后，健康检查通过：

```text
GET /api/health -> UP
```

消息观测接口通过：

```text
GET /api/admin/messaging/stats -> enabled=false, skipped=0
```

触发一次行为事件后：

```text
routingKey: behavior.recorded
status: skipped
payloadType: BehaviorRecordedEvent
message: messaging disabled
```

然后又跑了一轮目录压测，确认新增 MQ 模块没有拖慢公开商品目录链路：

```text
scenario: catalog
total: 500
concurrency: 60
ok: 500
failed: 0
errorRate: 0
RPS: 2190.14
p50: 23.58 ms
p95: 38.00 ms
p99: 57.79 ms
```

这个结果说明：默认关闭 RabbitMQ 时，新增消息模块不会影响已有读链路；目录接口仍然主要受三级缓存保护。

## 今天的收获

今天最大的收获是：消息队列不是为了“项目里多一个技术栈”，而是为了把系统拆出清晰边界。

三级缓存解决的是高频读问题；RabbitMQ 解决的是业务事件异步化问题；Agent 工作流解决的是导购决策链路可解释问题。它们不是互相替代，而是各自承担系统里的一个压力面。

当前 SmartMall AI 已经开始从“页面能跑”进入“系统能解释、能观测、能扩展”的阶段。

## 下一步

后续继续推进：

1. 真正启动 RabbitMQ，打开 `SMARTMALL_MESSAGING_ENABLED=true`，验证 `published` 和 `consumed` 链路。
2. 给 RabbitMQ 消费者增加并发、prefetch、重试间隔和 DLQ 处理策略。
3. 做一次行为事件压测，观察发布延迟、消费延迟、队列堆积和业务接口 p95。
4. 如果要保证更强可靠性，继续补 outbox 表，避免“数据库提交成功但 MQ 发布失败”的极端情况。
5. 后续秒杀模块可以继续用 Redis Lua 扣库存，再用 RabbitMQ 异步创建订单，实现削峰填谷。
