# 6.3 学习：SmartMall AI 商品服务端排序、缓存维度与压测验证

6.2 做完商品分页以后，商品货架已经不再一次性返回几万条数据。但分页之后马上会出现一个新问题：如果排序只在前端做，那么用户看到的只是“当前页内部排序”，并不是“全库排序后的第一页”。

真实电商里的“销量优先”“价格从低到高”“智能排序”都必须发生在服务端查询阶段。也就是说，数据库先根据排序规则选出整体结果，再分页返回给前端。今天就按 6.2 写下的后续计划，把 SmartMall AI 的商品排序继续往真实商城逻辑推进了一步。

## 今天做了什么

今天主要完成了四块内容：

1. 给 `GET /api/products` 增加 `sort` 参数，支持智能、销量、价格升序和价格降序。
2. 后端分页查询按排序规则在 MySQL 层完成，不再依赖前端临时排序。
3. 缓存 key 纳入 `sort` 维度，避免不同排序结果互相污染。
4. 前端商品页把排序写进 URL，刷新、翻页和分享链接后都能保留当前排序。

这次改动不算大，但它是商品货架从“可展示”走向“可运营”的一步。因为排序直接影响用户看到什么商品，也影响推荐、点击、购买和后续行为分值。

## 为什么不能只做前端排序

分页前，前端拿到所有商品，再排序虽然很粗糙，但表面上还能看到效果。分页后就不一样了：

```text
错误做法：
后端返回第 1 页 24 件商品
前端只对这 24 件商品排序
```

这样用户选择“价格从低到高”时，看到的只是第一页里最便宜的商品，而不是全站最便宜的商品。

今天改成了：

```text
正确做法：
后端根据 sort 构造排序条件
MySQL 在完整结果集上排序
后端返回排序后的第 N 页
前端只负责展示
```

这也是为什么电商系统里分页、排序、筛选必须放在同一条查询链路里设计，不能拆开做。

## 后端排序参数

商品接口现在支持：

```http
GET /api/products?page=1&pageSize=24&sort=smart
GET /api/products?page=1&pageSize=24&sort=sales
GET /api/products?page=1&pageSize=24&sort=priceAsc
GET /api/products?page=1&pageSize=24&sort=priceDesc
```

含义如下：

| sort | 含义 |
| --- | --- |
| `smart` | 按 AI 推荐分和销量综合排序 |
| `sales` | 按销量优先排序 |
| `priceAsc` | 按价格从低到高排序 |
| `priceDesc` | 按价格从高到低排序 |

如果前端没有传 `sort`，后端默认使用 `smart`。如果传入未知值，也会回退到 `smart`，避免非法参数影响接口稳定性。

## 缓存 key 继续细化

6.2 已经把缓存 key 从单纯的 `categoryId + keyword` 扩展到了：

```text
categoryId + keyword + page + pageSize
```

今天继续补上排序维度：

```text
categoryId + keyword + sort + page + pageSize
```

这样同一个关键词下：

- `手机 + smart`
- `手机 + sales`
- `手机 + priceAsc`
- `手机 + priceDesc`

会进入不同缓存槽。否则用户切换排序时，可能命中旧排序结果，页面看起来就会“排序按钮点了但没有变化”。

## MySQL 索引准备

为了给后续大数据量和高并发压测留好空间，今天也补了一份索引迁移脚本。重点覆盖：

- 智能排序：`status + ai_recommend_score + sales`
- 分类智能排序：`status + category_id + ai_recommend_score + sales`
- 价格排序：`status + price + sales + ai_recommend_score`
- 分类价格排序：`status + category_id + price + sales + ai_recommend_score`

这些索引不是为了“让今天的接口能跑”，而是为了后面数据继续变大时，查询计划不会轻易退化成大范围 filesort。

## 前端交互调整

前端商品页也同步做了几处细节：

- 排序下拉框切换时自动回到第一页。
- URL query 会保留 `sort`。
- 翻页时继续带着当前排序。
- 后端不可用时，fallback 商品也会按同样规则排序。

现在类似这样的链接可以直接打开：

```text
/products?keyword=手机&sort=priceAsc&page=2
```

这比只在内存里保存排序状态更可靠，也更接近真实电商的列表页体验。

## 验证结果

后端编译通过：

```bash
mvn -DskipTests package
```

前端构建通过：

```bash
npm run build
```

本地启动后端后，对 4 种排序各取 30 条样本验证：

| 排序 | 验证字段 | 首值 | 末值 | 结果 |
| --- | --- | --- | --- | --- |
| `priceAsc` | price | 29.00 | 34.35 | 通过 |
| `priceDesc` | price | 9028.93 | 9023.58 | 通过 |
| `sales` | sales | 5000 | 4998 | 通过 |
| `smart` | aiRecommendScore | 99 | 99 | 通过 |

这里 `smart` 的前 30 条推荐分都为 99，说明最高推荐分商品很多，后续可以继续叠加销量、用户偏好和类目多样性，让智能排序更细。

## 小规模压测

今天也把压测脚本的 catalog 场景改成包含排序参数的分页接口，然后跑了一轮轻量验证：


## 今天的收获

今天最重要的收获是：分页不是一个孤立功能，它会把搜索、排序、筛选、缓存、索引全部串起来。

如果只做分页，不处理排序，用户体验会变假；如果只处理排序，不更新缓存 key，结果可能会变脏；如果排序和分页都有了，但没有索引，数据量上来以后查询又会慢。

所以真实项目里的优化往往不是“加一个功能”，而是沿着一条业务链路把每个环节都补齐。
