# 6.4 学习：SmartMall AI 三级缓存深化与导购 Agent 工作流优化

6.3 做完商品分页后的服务端排序以后，SmartMall AI 的商品货架已经更接近真实电商平台。但如果继续往商业级系统推进，光有分页和排序还不够，接下来要继续补两个核心能力：

1. 缓存不能只是“能命中”，还要能抗穿透、抗击穿、抗集中失效。
2. AI 助手不能只是“一个大 prompt”，而要像真实 Agent 一样有路由、记忆、工具调用、校验和可观测工作流。

所以今天主要做两条线：三级缓存架构继续工程化，导购 Agent 工作流继续结构化。

## 参考了哪些 Agent 做法

我先看了几个成熟 Agent 框架和 Spring AI 的官方资料。

LangGraph 的定位不是简单聊天，而是面向长任务、状态化 Agent 的编排运行时，强调持久执行、流式、人类参与和状态持久化：<https://docs.langchain.com/oss/python/langgraph/overview>

LangGraph 对 workflow 和 agent 的区分也很有启发：workflow 更确定，agent 更自主；agent 通常是 LLM 在工具反馈循环里自主决定下一步：<https://docs.langchain.com/oss/python/langgraph/workflows-agents>

Spring AI 的工具调用文档强调一点：模型只负责提出工具调用请求，真正执行工具和返回结果的是应用程序本身。这正好适合电商场景，因为商品、价格、库存必须由后端真实数据决定：<https://docs.spring.io/spring-ai/reference/api/tools.html>

Spring AI 的 Chat Memory 文档也提到，推荐使用 `MessageChatMemoryAdvisor` 把历史对话作为结构化消息传入，而不是粗暴塞进 system prompt：<https://docs.spring.io/spring-ai/reference/api/chat-memory.html>

另外 Spring AI 关于 AutoMemoryTools 的文章把记忆分成两层：短期会话记忆保存当前对话窗口，长期记忆保存值得跨会话保留的用户偏好、项目事实和行为反馈：<https://spring.io/blog/2026/04/07/spring-ai-agentic-patterns-6-memory-tools/>

这些资料给我的结论是：SmartMall AI 现阶段不需要直接引入一个完整 LangGraph，但应该吸收它的工作流思想，把导购助手从“提示词堆叠”改成“显式节点 + 工具调用 + 记忆 + 校验”的结构。

## 三级缓存继续深化

之前 SmartMall AI 已经有：

```text
L1 Caffeine 本地缓存
  -> L2 Redis 分布式缓存
  -> L3 MySQL 权威数据源
```

今天继续补了四个生产化细节。

### 1. 空值缓存

如果用户不断请求不存在的 key，普通缓存不会命中，每次都会穿透到 MySQL。今天增加了空值哨兵：

```text
__SMARTMALL_NULL__
```

当 loader 返回空值时，系统会把空值写入本地缓存和 Redis，Redis 空值 TTL 默认更短，避免长期污染缓存。

### 2. 热点 key 回源锁

缓存击穿经常发生在热点 key 过期瞬间。比如首页推荐或者商品第一页同时过期，几百个请求一起进来，如果每个请求都查 MySQL，就会把数据库打穿。

今天给 `MultiLevelCacheService` 增加了按 key 粒度的回源锁：

```text
同一个 key miss
  -> 第一个线程回源 MySQL
  -> 其他线程等待或复查缓存
  -> 回源结果写入 Caffeine + Redis
```

这样同一时间只有一个线程负责重建热点缓存。

### 3. Redis TTL 抖动

如果所有缓存都是 600 秒过期，那么启动预热的一批 key 也会在同一秒集中失效。今天给 Redis TTL 加了 jitter：

```text
redis ttl = base ttl + random(0, jitter)
```

这样可以降低缓存雪崩概率。

### 4. 启动预热

新增了 `CatalogCacheWarmupRunner`，应用启动后异步预热：

- 商品分类
- 首页推荐
- `smart / sales / priceAsc / priceDesc` 排序第一页
- 手机、电脑、食品等高频分类第一页

本地验证时，预热大约 1 秒完成。

## Agent 工作流优化

今天把导购 Agent 的主流程整理成：

```text
Route
  -> Rewrite
  -> Memory
  -> Tool / Retrieve
  -> Validate
  -> Answer
  -> Remember
```

每个节点都会写入 `agentSteps`，前端可以展示“AI 到底做了什么”。这比只展示一句回答更接近真实智能客服系统，也方便后续调试。

### Route

先判断用户输入是身份问题、问候、商品导购、追问，还是需要快速确定性检索。

比如“你是谁”不应该进入商品推荐；“有没有 400 元左右的手机”可以直接走快速商品召回，减少模型等待时间。

### Rewrite

把用户原话改写成更利于检索的提示词：

```text
有没有400元左右的手机推荐一下
-> 有没有400元左右的手机推荐一下；预算约 400 元；目标品类：手机数码
```

如果启用了真实大模型，复杂问题可以走模型改写；本地默认走确定性改写，保证速度。

### Memory

保留原来的 QKV 思路：

- Query：用户原话和改写后的检索意图
- Key：预算、品类、品牌、用途等关键词
- Value：本轮回答摘要和推荐商品

当历史上下文过长时，会压缩进摘要，避免对话越聊越慢。

### Tool / Retrieve

Spring AI Agent 现在可以调用商城工具：

- `search_products`
- `get_product_detail`
- `recommend_for_current_user`
- `get_recent_orders`
- `compare_products`

同时我也优化了工具内部实现：`search_products` 不再先拉全量商品再过滤，而是优先走分页查询和服务端排序，减少大表压力。

### Validate

推荐前会做约束校验：

- 问手机，就不能推荐耳机、云台、平板。
- 问更便宜，就必须低于上一轮参考价格。
- 问某品牌，如果商品库没有，就明确说没有，不跨品牌乱推荐。

### Answer 和 Remember

最后生成面向用户的回答，然后把本轮 Query/Key/Value 写回记忆。前端也能看到：

```text
Route 节点
Rewrite 节点
Memory 节点
Retrieve 节点
Tool 节点
Answer 节点
Remember 节点
```

这样助手的问题不再只是“回答好不好”，而是能拆成每个节点逐步调试。

## 今天的收获

今天最大的感受是，工程里的“智能”不是靠一句大 prompt 堆出来的。

缓存系统要把异常场景考虑清楚：穿透、击穿、雪崩、预热、统计。

Agent 系统也要把过程拆清楚：路由、改写、记忆、工具、校验、回答、写回。

当这些节点都能被观察、被验证、被压测时，项目才会从“能演示”慢慢变成“能解释、能维护、能优化”。
