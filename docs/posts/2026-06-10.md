# 6.10 学习：SmartMall AI DLQ 管理、秒杀状态持久化与 5000 混合流量压测

昨天给自己留下的任务比较明确：继续把 SmartMall AI 的 RabbitMQ / outbox / 秒杀链路从“能跑”推进到“能看、能查、能恢复、能压测”。今天主要围绕五件事展开：

1. 管理员能看 DLQ，也能安全重投死信消息。
2. 秒杀请求状态落到 MySQL，让异步建单结果可查询。
3. 后台能看到 HikariCP、MySQL status、慢查询计数和 EXPLAIN。
4. 做混合流量压测，而不是只压单一接口。
5. MQ 后台面板继续补全图表和运维信息。

## 今天完成的内容

### 1. DLQ 查看与安全重投

之前后台只能看到队列深度，还不能直接看死信消息。今天新增了两个管理员接口：

```text
GET  /api/admin/messaging/dlq?limit=10
POST /api/admin/messaging/dlq/requeue?limit=20
```

查看 DLQ 时使用 RabbitMQ Management API 的 `ack_requeue_true`，只做预览，不会把消息误 ack 掉。

重投时通过 RabbitTemplate 从 `smartmall.events.dlq` 取消息，优先从 `x-first-death-routing-key` 或 `x-death.routing-keys` 找回原 routing key，再投回 `smartmall.events`。今天拿历史死信做了一次验证：

```json
{
  "requested": 1,
  "requeued": 1,
  "skipped": 0,
  "errors": 0
}
```

重投后没有新增 publish / consume failure，DLQ 从 8 条下降到 7 条。

### 2. 秒杀请求状态持久化

之前秒杀状态只写在 Redis 里，适合快速幂等和限购，但不适合做订单结果查询、后台排障和用户侧轮询。今天新增了一张表：

```text
mall_seckill_request
```

关键字段包括：

```text
request_id
user_id
product_id
quantity
status
remaining_stock
order_id
order_no
failure_reason
completed_at
```

现在秒杀链路变成：

```text
requestId 幂等检查
-> user-product 限购检查
-> Redis Lua 扣库存
-> 写 seckill request = QUEUED
-> 写 outbox: seckill.order.requested
-> RabbitMQ 消费者异步创建订单
-> 写 seckill request = ORDERED
```

新增用户查询接口：

```text
GET /api/seckill/orders/{requestId}
```

后续前端可以在提交秒杀后轮询这个接口，展示“排队中、已生成订单、失败、已重复请求”等状态。

本地压测后状态表分布：

```text
ORDERED             210
ALREADY_REQUESTED   660
```

这说明进入异步建单的请求已经成功回写订单状态，同一用户重复抢同一商品的请求也被记录成了可解释状态。

### 3. 性能快照接口

今天新增了后台性能接口：

```text
GET /api/admin/performance/snapshot
GET /api/admin/performance/explain/products
GET /api/admin/performance/explain/orders
GET /api/admin/performance/explain/behaviors
```

它们主要用来做压测后的定点观察：不是只看接口响应时间，还要看数据库连接池、MySQL 线程、慢查询计数和代表性 SQL 的执行计划。

5000 混合流量压测后抓到的快照：

```text

Hikari idle: 21
Hikari total: 30
threadsAwaiting: 0
Slow_queries: 0
Threads_running: 10
```

EXPLAIN 里看到：

- 商品列表命中 `idx_product_status_score_sales`
- 订单列表命中 `idx_order_created_desc_id_desc`
- 用户行为列表命中 `idx_behavior_user_created_desc_id_desc`

其中订单查询还有 `Using where`，说明后续还能继续针对订单查询做更细的索引和 SQL 分流。

### 4. 管理员后台 MQ 可视化

后台消息队列页今天新增了：

- `Dead Letter Queue`：查看死信 routing、原因、payload 预览，并支持重投。
- `DB Performance Snapshot`：展示 Hikari 连接池、慢查询、Threads、Questions。
- `Routing Key Stats` 条形图：按 `behavior.recorded`、`order.created`、`seckill.order.requested` 看吞吐和失败。

浏览器里验证过页面，MQ 页包含这些模块：

```text

RabbitMQ Queue Depth
Dead Letter Queue
DB Performance Snapshot
Routing Key Stats
```

路由统计条也正常渲染了 3 条。

## 5000 条混合流量压测

今天新增脚本：

```text
scripts/load-mixed-traffic.mjs
```

这次不再只压单接口，而是混合四类真实电商流量：

```text
商品浏览
行为埋点
普通下单
秒杀请求
```

运行命令：

```bash
node scripts/load-mixed-traffic.mjs \
  --total 5000 \
  --concurrency 160 \
  --users 200 \
  --output docs/perf-results/mixed-traffic-5000-20260610.json
```

整体结果：

```text
total: 5000
concurrency: 160
rps: 1080.04
failed: 0
errorRate: 0
```

分流量结果：

| 流量类型 | 请求数 | 成功 | 失败 | p95 | p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 商品浏览 | 2250 | 2250 | 0 | 209.95ms | 315.64ms |
| 行为埋点 | 1000 | 1000 | 0 | 268.28ms | 358.05ms |
| 普通下单 | 1000 | 1000 | 0 | 286.91ms | 366.31ms |
| 秒杀请求 | 750 | 750 | 0 | 293.79ms | 438.03ms |

脚本刚结束时 outbox 曾短暂堆积 1488 条，这是异步削峰的正常表现。等待 15 秒后重新观察：

```text
outbox.pending = 0
outbox.failed = 0
behavior queue ready/unacked = 0/0
order queue ready/unacked = 0/0
seckill queue ready/unacked = 0/0
```

也就是说，请求高峰过后，outbox 和 RabbitMQ 队列可以自然排空。

## 今天学到的东西

今天最明显的体会是：电商系统里的“高并发优化”不能只看接口本身。

比如秒杀接口看起来返回很快，但真正重要的是：

- Redis 扣库存是否原子。
- requestId 是否幂等。
- 同一用户是否能重复占库存。
- outbox 是否可靠落库。
- RabbitMQ 是否能及时消费。
- 消费失败后库存是否补偿。
- 用户是否能查询异步订单结果。
- 管理员是否能看到 DLQ、队列堆积和数据库状态。

这些东西串起来之后，系统才开始有一点真实生产系统的味道。
