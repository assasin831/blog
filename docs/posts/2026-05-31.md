# 5.31 学习：SmartMall AI 部署、调试与博客上线复盘

5 月 31 日这一天，工作的重点从“继续写功能”转向了“让项目真正跑在远端环境里”。这和本地开发完全不是一个难度：本地只要前端、后端、数据库都能启动，页面能打开，就会觉得项目已经完成了；但真正部署到服务器之后，端口、进程、反向代理、数据库权限、跨域、安全策略、静态资源路径都会一起浮出来。

这一天最有价值的收获是：SmartMall AI 不再只是本地能演示的商城项目，而是开始进入一个更接近真实工程的状态。同时，我也把这些调试过程沉淀到了个人博客里，让每天的开发记录不只停留在聊天窗口和临时笔记中。

![SmartMall AI 首页截图](/images/smartmall/home.png)

## 当天目标

5.31 的目标主要有四个：

1. 把 SmartMall AI 智能商城部署到远端服务器，并能通过公网地址访问。
2. 调通前端、后端、MySQL、Redis、Nginx 之间的访问链路。
3. 修复登录失败、跨域、旧进程残留、端口冲突等部署问题。
4. 把 5.30 的项目复盘和 GitHub Pages 博客搭建过程整理成个人博客内容。

这个过程让我意识到，一个项目真正走向可展示状态时，难点不只是“代码写没写完”，而是“系统能不能在另一个环境里稳定、可重复地跑起来”。

## SmartMall AI 部署链路

SmartMall AI 当前是一个前后端分离项目：

- 前端：Vue，负责商城页面、购物车、登录注册、AI 助手、管理员页面等交互。
- 后端：Spring Boot，负责用户、商品、订单、余额、收藏、评论、AI 导购等接口。
- 数据库：MySQL，保存用户、商品、订单、评论、行为分值等核心业务数据。
- 缓存：Redis，作为后续多级缓存和高并发优化的基础。
- 网关与静态服务：Nginx，负责托管前端静态文件，并把 `/api` 请求反向代理到后端。

部署后的简化链路是：

```txt
浏览器
  -> Waas 公网 HTTPS 地址
  -> 平台 HTTP 端口映射
  -> Nginx
  -> Vue 静态页面
  -> /api 反向代理
  -> Spring Boot 后端
  -> MySQL / Redis
```

本地开发阶段，前端通常跑在 Vite 开发服务器上，后端跑在 Spring Boot 本地端口，数据库也在本机。这种模式很适合快速迭代，但不适合直接给别人访问。部署时需要把前端构建成静态文件，把后端打成可运行的 jar，再用 Nginx 统一入口。

## 端口选择与 Waas 映射

服务器平台要求开放端口在 `1024 - 65535` 之间。最开始容易想到 `8080`、`8088`、`8888` 这些常见端口，但实际排查后发现，服务器环境里有些端口已经被平台自带服务占用，例如 code-server 或其他管理进程。

最终采用的方式是：

- Spring Boot 后端使用内部端口 `18080`。
- Nginx 对外监听 `18081`。
- Waas 平台把公网 HTTPS 地址映射到服务器的 HTTP `18081`。
- Nginx 把 `/api` 转发到 `127.0.0.1:18080`。

这样前端和接口都能从同一个公网域名访问，浏览器不会再因为前后端域名不一致而触发复杂的跨域问题。同时，后端端口不直接暴露给用户，入口统一收口在 Nginx 上，部署结构也更清晰。

## 部署脚本

为了避免每次手动复制文件、杀进程、重启服务，我把部署流程整理进了脚本。脚本主要做这些事情：

1. 构建前端，生成静态资源。
2. 构建后端，生成 Spring Boot jar。
3. 上传或更新服务器上的项目文件。
4. 更新 Nginx 配置。
5. 初始化或修复数据库种子数据。
6. 停掉旧后端进程并启动新后端进程。
7. 检查前端页面和登录接口是否可用。

这一步很重要，因为部署如果只靠手动操作，很容易出现“我这次改了，但下次忘了”的问题。脚本化之后，部署过程才有可复现性。

## 调试记录

部署时遇到的第一个问题是公网地址打开异常。表面上看只是页面访问失败，但实际原因可能在很多层：

- 平台端口没有正确映射。
- Nginx 没有启动。
- Nginx 监听了错误端口。
- 后端没有启动。
- `/api` 代理地址写错。
- 防火墙或平台网关拒绝请求。

排查时不能只盯着浏览器页面，需要一层一层确认：

```txt
公网地址是否能到平台
服务器端口是否在监听
Nginx 是否能返回静态页面
/api 是否能转发到后端
后端是否能连接 MySQL 和 Redis
数据库里是否有正确的测试用户
```

这也是部署最像真实工程的地方：前端报一个错误，真正的问题可能在网关、Nginx、后端、数据库、配置文件中的任何一层。

## 旧进程残留问题

调试登录接口时，还遇到过一个很典型的问题：代码已经改了，重新部署后接口表现却还是旧的。后来发现是旧的后端进程没有被正确停止，新 jar 没有真正接管服务。

这个问题的迷惑性很强，因为你会下意识怀疑代码、数据库、浏览器缓存，但真正原因是服务器上还在跑旧进程。

最后的处理方式是：

- 部署脚本里明确查找并停止旧的 Spring Boot 进程。
- 启动新进程后检查监听端口。
- 通过接口返回结果确认当前服务确实是新版本。

这个经验很实用：以后只要遇到“我明明改了但线上没变化”，第一件事就应该确认当前运行进程是不是新构建产物。

## MySQL 与数据初始化

部署后，数据库也不是简单建表就结束。SmartMall AI 需要有基础商品、用户、管理员账号、订单、收藏、评论等演示数据，才能完整展示商城行为。

这一天对数据库做了几件事：

- 初始化商品、用户和管理员数据。
- 确认登录用户和管理员用户都能从数据库读取。
- 修复旧种子数据里的密码存储方式。
- 给后续数据库调优、索引设计、行为分值推荐预留方向。

在这个项目里，数据库不只是“存数据”，它会逐渐成为推荐、订单、用户画像和运营后台的核心。后面如果做高并发优化，MySQL 的索引、慢查询、分页查询、冷热数据拆分都会变成很重要的内容。

## CORS 跨域问题

登录不上时，曾经出现过一个很容易误判的问题：用命令行直接请求接口可以成功，但浏览器里登录失败。

这说明后端本身并不是完全不可用，问题很可能和浏览器环境有关。最后定位到是 CORS 配置没有允许当前 Waas 公网域名。浏览器会带上 `Origin`，后端如果不允许这个来源，就会拒绝请求。

修复方式是在 Spring Boot 的 CORS 配置里允许当前部署域名，并使用 `allowedOriginPatterns` 适配平台生成的访问地址。修复后，公网页面上的登录请求可以正常通过。

这个坑提醒我：浏览器请求和命令行请求并不完全一样。尤其是带登录、Cookie、Token、跨域的时候，必须按真实浏览器环境来测。

## 密码加密方案

这一天还重点处理了登录安全问题。最开始发现数据库种子用户使用了 `{noop}` 形式，也就是等价于明文密码存储。这在练习阶段能跑，但绝对不能作为正式系统方案。

中间曾经考虑过前端 MD5。它看起来像“加密”，但本质上并不能解决密码安全问题：

- MD5 不是安全的密码哈希算法。
- 前端 MD5 后，MD5 值本身就会变成新的登录凭证。
- 一旦数据库泄漏，攻击者仍然可以利用这些固定摘要尝试撞库。
- 如果没有 HTTPS，传输过程依然可能被窃听或篡改。

最终采用的方案是：

- 依赖 HTTPS 保护传输过程。
- 前端提交用户输入的原始密码，不在前端做 MD5。
- 后端使用 Spring Security 的 `PasswordEncoder`。
- 数据库存储 bcrypt 哈希，不存明文。
- 登录时由后端用 bcrypt 校验原始密码和数据库哈希是否匹配。

也就是说，正式系统里密码安全的核心不是“前端把密码变一遍”，而是：

```txt
HTTPS 保护传输
后端安全哈希
数据库只存不可逆哈希
登录校验由后端完成
```

如果后续继续加强，可以把 bcrypt 升级为 Argon2，加入密码强度策略、登录失败限流、验证码、异常登录提醒等能力。

## 登录验证结果

修复后做了两类验证：

- 使用真实密码登录可以成功。
- 使用旧的 MD5 摘要登录会失败。

这说明系统已经从“前端摘要登录”回到更正规的“HTTPS + 后端 bcrypt 校验”模式。对一个商城系统来说，这一步虽然不如 UI 改版那么直观，但它决定了项目有没有继续向正式系统发展的基础。

## 管理员与用户系统

部署过程中也再次确认了一个方向：商城不应该只有用户端。真实电商平台至少需要两套视角：

- 用户端：浏览商品、搜索、收藏、评论、购物车、下单、余额支付、客服咨询、账户中心。
- 管理员端：商品管理、用户管理、订单处理、评论审核、客服消息、运营看板、库存与数据维护。

5.31 的部署工作虽然主要在服务器和安全链路上，但它也让管理员端的重要性更明显。只有把用户端、管理员端、数据库、接口、安全、部署这些部分连在一起，项目才会像一个完整系统，而不是几个分散页面。

## AI 导购 Agent 的工程意义

SmartMall AI 里最有特色的功能是 AI 导购助手。前一天已经对 Agent 做过不少优化，比如：

- 根据用户预算、品类、品牌、用途筛选商品。
- 对“更便宜一点”“有没有同类产品”这类上下文问题做理解。
- 在回答中展示真实商品卡片，而不是只给空泛建议。
- 引入类似 Prompt 改写、Key 提取、Memory 命中、Value 写入的工作流展示。
- 当问题不属于商品推荐时，避免胡乱推荐无关商品。

部署到公网后，Agent 的意义会更明显：别人可以直接打开页面体验商城导购，而不是只看本地截图。后续如果接入更稳定的模型 API，再加上商品向量检索、用户行为画像和上下文压缩，它就可以继续往真实电商客服和导购系统靠近。

## 博客搭建与 GitHub Pages

5.31 的另一条线是个人博客。博客使用 VitePress 搭建，内容用 Markdown 编写，通过 GitHub Pages 托管。

整体流程是：

```txt
Markdown 文章
  -> VitePress 构建
  -> GitHub Actions 自动部署
  -> GitHub Pages 生成静态网站
  -> 通过 https://assasin831.github.io/blog/ 访问
```

这个方案非常适合记录学习过程。它不需要自己维护服务器，推送到 GitHub 后就能自动构建和发布。对我来说，博客现在承担三个作用：

1. 每日记录：记录今天做了什么、遇到什么问题、怎么解决。
2. 项目复盘：把 SmartMall AI 这样的项目写成可展示的作品。
3. 学习笔记：把 GitHub Pages、部署、数据库、缓存、压测这些知识整理成体系。

## GitHub Pages 的 404 问题

博客上线时也遇到了 404。原因是 GitHub Pages 项目站点不是部署在根路径，而是部署在 `/blog/` 这个 base 路径下。

例如：

```txt
正确路径：
https://assasin831.github.io/blog/posts/2026-05-30

错误路径：
https://assasin831.github.io/posts/2026-05-30
```

如果页面里的链接写错前缀，本地可能看起来没问题，但线上就会跳到错误路径。后来统一修复了导航、首页入口和文章链接，让每日记录、项目笔记、学习笔记都能正确访问。

这个问题和部署 SmartMall AI 时的路径问题很像：本地环境和线上环境经常不一样，不能只用本地结果判断项目是否真的可用。

博客搭建后，也对界面做了几轮打磨：

这些视觉优化虽然不是核心功能，但对个人博客很重要。一个博客如果只是默认模板，会像“文档仓库”；如果有自己的视觉风格，就更像一个长期维护的个人空间。

## 当天最大的收获

这一天最明显的收获是：部署不是最后一步，而是系统开发的一部分。

本地开发时，很多问题会被隐藏起来：

- 端口默认可用。
- 数据库就在本机。
- 跨域可以通过开发代理绕过去。
- 旧进程通常不会残留。
- 密码安全容易被“先能跑”掩盖。
- 静态资源路径不一定暴露问题。

一旦部署到服务器，这些问题就会全部变成真实问题。它们迫使我从“写页面和接口”切换到“维护一个系统”的角度去思考。

## 后续计划

SmartMall AI 后续可以继续推进这些方向：

1. Redis 多级缓存：本地缓存 + Redis + 数据库兜底，降低高并发下数据库压力。
2. 数据库调优：商品搜索、订单查询、用户行为表增加索引和慢查询分析。
3. 压测报告：使用 JMeter 或 k6 模拟并发请求，记录 QPS、响应时间和错误率。
4. 推荐系统：根据点击、收藏、加购、购买、评论等行为计算用户偏好分值。
5. Agent 强化：增加商品检索工具、上下文压缩、品牌识别、无结果兜底回复。
6. 安全增强：登录限流、验证码、管理员权限校验、敏感配置环境变量化。
7. CI/CD：把构建、测试、部署流程进一步自动化。

博客后续也会继续记录每天的开发内容。相比临时笔记，博客更适合复盘，因为它会逼着我把“做过什么”整理成“为什么这么做、怎么排查、以后怎么避免”。

## 小结

5.31 这一天做的事情看起来很杂：部署、端口、Nginx、MySQL、Redis、CORS、密码加密、博客发布、页面 404 修复。但这些事情其实都指向同一个目标：把项目从本地练习变成可访问、可解释、可持续维护的作品。

SmartMall AI 还没有到真正商业级系统的程度，但它已经开始具备商业级系统需要考虑的问题：部署链路、账号安全、数据库结构、用户行为、管理员后台、AI 导购、缓存和高并发优化。接下来要做的，就是继续把这些问题一个个补齐。
