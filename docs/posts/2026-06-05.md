# 6.5 学习：SmartMall AI 缓存热点观测与 Agent 审计链路完善

6.4 做完三级缓存深化和导购 Agent 工作流之后，我在下一步计划里写了几件事：做缓存预热对比、增加 Redis key 监控、保存 Agent 工具调用审计、继续做更大并发压测。

今天先把其中最能提高项目可观测性的部分落地：让缓存系统不只是“有命中率”，而是能看到每个 key 的访问热度；让 Agent 不只是“给回答”，而是能留下每轮工作流和工具调用审计。

## 今天做了什么

今天主要完成了四块：

1. 增加缓存热点 key 统计。
2. 增加 Redis catalog key 快照接口。
3. 增加 Agent 工作流和工具调用审计日志。
4. 增加观测脚本，并跑了一轮 500 请求、60 并发的目录压测。

这些改动都不是为了让页面多一个按钮，而是为了后续做性能调优时能回答几个问题：

- 哪些缓存 key 最热？
- 热点 key 是命中 Caffeine、Redis，还是反复回源 MySQL？
- Redis 里到底有哪些目录缓存？
- TTL 是否分散？
- AI 助手每轮经过了哪些节点？
- 如果模型调用了工具，工具入参、结果数量和耗时能不能追踪？

## 缓存热点 key 统计

6.4 只有全局缓存指标，例如：

```text
localHits
redisHits
misses
protectedLoads
lockTimeouts
hitRate
```

这些指标能说明整体缓存是否有效，但不能告诉我“哪个 key 最热”。今天给 `MultiLevelCacheService` 增加了按 key 粒度的指标：

```text
localHits
redisHits
misses
writes
nullWrites
protectedLoads
lockTimeouts
totalReads
hitRate
lastAccessAt
```

新增接口：

```http
GET /api/cache/catalog/hot-keys?limit=20
```

它会按访问次数排序，返回当前进程内最热的目录缓存 key。

这对后续压测很重要。比如如果首页推荐、分类第一页、商品详情页长期排在前面，就说明这些 key 值得做更强的预热、更长的 TTL 或专门的热点保护。

## Redis key 快照

今天还加了 Redis catalog key 快照接口：

```http
GET /api/cache/catalog/redis-keys?limit=50
```

返回信息包括：

```text
key
ttlSeconds
valueBytes
nullValue
```

这样可以直接看到：

- Redis 里有哪些 `smartmall:catalog:*` key。
- 每个 key 还剩多少 TTL。
- value 大小是多少。
- 有没有空值哨兵。

6.4 做了 TTL 抖动，但如果没有观测接口，就很难确认 TTL 是否真的分散。今天这个接口就是为后面做缓存预热 on/off 和 TTL 分布分析准备的。

## Agent 工作流审计

6.4 已经把 Agent 工作流拆成：

```text
Route -> Rewrite -> Memory -> Tool/Retrieve -> Validate -> Answer -> Remember
```

今天继续补“审计日志”。新增 `AgentAuditService`，先用内存队列保存最近记录，默认最多 300 条。

工作流审计会保存：

```text
userId
mode
toolEnabled
rawMessage
optimizedPrompt
recommendationCount
productIds
productNames
agentSteps
qkvTrace
latencyMillis
```

管理员接口：

```http
GET /api/admin/assistant/audits/stats
GET /api/admin/assistant/audits/workflows
```

这样如果用户说“AI 又答错了”，后端可以查到这轮到底识别了什么预算、召回了哪些商品、QKV 命中了什么记忆、最后用了本地规则还是 Spring AI Agent。

## 工具调用审计

今天也把工具调用审计接进了 `MallAssistantTools`。

目前可审计的工具包括：

- `search_products`
- `get_product_detail`
- `recommend_for_current_user`
- `get_recent_orders`
- `compare_products`

每次工具被模型调用时，会记录：

```text
toolName
arguments
resultCount
resultSummary
latencyMillis
```

管理员接口：

```http
GET /api/admin/assistant/audits/tools
```

本地默认没有启用真实大模型，所以这次验证中 `toolAuditSize = 0` 是正常的；一旦启用 Spring AI 工具调用，工具结果就会进入审计队列。

## 新增观测脚本

为了减少手工 curl，今天新增脚本：

```bash
node scripts/observe-cache-agent.mjs --baseUrl http://127.0.0.1:8080 --limit 5
```

它会自动做几件事：

1. 登录普通用户和管理员。
2. 访问几个商品分页接口。
3. 向 AI 助手发送一条导购问题。
4. 拉取缓存全局统计。
5. 拉取 hot key 排名。
6. 拉取 Redis key 快照。
7. 拉取 Agent 审计统计、最近工作流和最近工具调用。

这个脚本后续可以接到压测流程里：压测前跑一次，压测后跑一次，就能看到命中率、热点 key 和审计队列的变化。

## 500 请求压测

今天把 catalog 场景提高到：

```text
total: 500
concurrency: 60
```

结果：

```text
ok: 500
failed: 0
errorRate: 0
RPS: 2071.71
p50: 23.23 ms
p90: 41.89 ms
p95: 44.29 ms
p99: 57.32 ms
```

这轮比 6.4 的 160 请求、24 并发更接近压力观察。p95 上升是正常的，因为并发数提高到了 60；更重要的是没有错误，缓存锁等待为 0，Redis 失败为 0，热点 key 命中率接近 98%。

## 今天的收获

今天的重点不是“再加一个缓存”，而是把缓存变得可观察。

以前看到 hitRate 高，只能知道整体缓存有效；现在能看到具体哪个 key 热、哪个 key miss、哪个 key 被单飞锁保护、Redis 里哪个 key 的 TTL 还剩多少。

Agent 也是一样。以前只能看最终回答；现在可以查工作流审计，看到原始问题、改写结果、商品候选、QKV trace、节点链路和耗时。

一个系统越往后做，越不能只依赖“感觉它能跑”。能观测、能解释、能复盘，才是继续优化的基础。
