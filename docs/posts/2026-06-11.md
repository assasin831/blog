# 6.11 学习：SmartMall AI 秒杀状态闭环、DLQ 精准重投与订单查询优化

昨天留下的任务主要是把 RabbitMQ / outbox / 秒杀链路继续往“真实可查、真实可恢复”推进。今天没有继续堆功能，而是围绕几个生产系统里很关键的细节打磨：

1. 用户提交秒杀后，前端能看到异步建单进度。
2. 管理员能查秒杀请求，而不是只看 RabbitMQ 队列。
3. DLQ 重投不能只做粗暴批量按钮，要能确认、筛选和指定消息。
4. 订单查询继续补索引，压测后能自动采集 slow log 和 explain。

## 用户端：秒杀状态轮询闭环

之前秒杀接口已经把请求状态落到了 `mall_seckill_request`，但是前端还没有接上，所以用户点击之后只能看到“请求已提交”，不知道最后到底有没有生成订单。

今天新增了前端 `seckill` API：

```ts
POST /api/seckill/orders
GET  /api/seckill/orders/{requestId}
```

商品详情页新增了“秒杀抢购”入口。用户点击后会生成一个 `requestId`，提交秒杀请求，然后每 1.5 秒轮询一次状态，直到进入终态：

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 请求进入预处理 |
| `QUEUED` | 已进入 outbox / RabbitMQ 异步建单队列 |
| `ORDERED` | 异步订单已创建 |
| `FAILED` | 建单失败，库存进入补偿流程 |
| `SOLD_OUT` | Redis 扣库存时发现库存不足 |
| `ALREADY_REQUESTED` | 同一用户已经请求过同一商品 |
| `DUPLICATE_REQUEST` | requestId 被幂等保护拦截 |

这样用户侧就不再是“点一下没反应”，而是能看到异步系统正在推进到哪一步。

## 管理员后台：秒杀请求列表

后台新增了秒杀请求查询接口：

```text
GET /api/admin/seckill/requests
```

支持按下面条件过滤：

- `status`
- `userId`
- `productId`
- `requestId`
- `orderNo`
- `limit`

管理员页面在 RabbitMQ / Outbox 监控页里增加了 `Seckill Requests` 面板，可以直接看到：

- requestId
- status
- userId
- productName
- remainingStock
- orderNo
- updatedAt

这样排障时链路会清楚很多。比如用户反馈“我参与秒杀了但订单没出来”，后台可以先查 `requestId`，再看是停在 `QUEUED`、已经 `ORDERED`，还是失败后进入补偿。

## DLQ：从批量重投到精准重投

之前 DLQ 只有一个批量 requeue 按钮，虽然能用，但太容易误操作。

今天做了三层保护：

1. 前端点击重投时必须二次确认。
2. 后端接口要求 `confirm=true`，否则不会真正消费 DLQ。
3. 支持指定 `routingKey` 和 `payloadHash`。

新的重投接口支持：

```text
POST /api/admin/messaging/dlq/requeue?limit=10&confirm=true
POST /api/admin/messaging/dlq/requeue?payloadHash=xxx&confirm=true
POST /api/admin/messaging/dlq/requeue?routingKey=seckill.order.requested&confirm=true
```

后台 DLQ 表格也会展示 payload hash 的短码，并提供单条重投按钮。这样管理员可以只重投某一条消息，而不是把整批死信全部重新打回业务队列。

## 订单查询与慢查询采集

6.10 的 explain 里订单查询还有 `Using where`，今天继续补了订单索引：

```sql
idx_order_user_created_id_desc(user_id, created_at DESC, id DESC)
idx_order_status_created_id_desc(status, created_at DESC, id DESC)
idx_order_no(order_no)
```

同时给秒杀请求表补了运维查询索引：

```sql
idx_seckill_product_status_time(product_id, status, updated_at DESC)
idx_seckill_order_no(order_no)
```

这些索引主要服务两个场景：

- 用户中心按用户倒序查询订单。
- 管理后台按状态、订单号、商品和秒杀状态做排障查询。

性能观测方面新增：

```text
GET /api/admin/performance/slow-log
```

如果 MySQL 开启了 `log_output=TABLE`，就可以直接读取 `mysql.slow_log`；如果没开，也会返回可见的错误信息，不影响主链路。

压测脚本 `load-mixed-traffic.mjs` 也补充了 slow log 采集，另外新增了独立脚本：

```bash
node scripts/capture-performance-snapshot.mjs \
  --baseUrl http://localhost:8080 \
  --output docs/perf-results/performance-snapshot-20260611.json
```

以后不一定要跑完整压测，也可以单独保存一次 HikariCP、MySQL status、slow log、explain、MQ 和 outbox 快照。

## 今天的收获

今天最明显的感受是：异步系统不能只关注“消息有没有发出去”，还要能回答三个问题：

- 用户怎么知道结果？
- 管理员怎么查到状态？
- 失败消息怎么安全恢复？

秒杀、outbox、RabbitMQ、DLQ、MySQL 索引和后台可视化连起来之后，系统才不只是一个 Demo，而是开始接近真实业务系统里的可运营形态。
