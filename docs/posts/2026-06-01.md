# 6.1 学习：SmartMall AI 线上访问恢复、Waas 部署与数据库迁移排障

这一天主要围绕 SmartMall AI 的线上可访问性继续推进。前面已经把智能商城部署到了 Waas 服务器，但后续再次访问时发现线上链接打不开，外部页面返回 `502 Bad Gateway`。这类问题看起来像“网页挂了”，实际可能出现在平台端口映射、Nginx、后端进程、数据库迁移、静态资源路径等很多层。

这次处理的目标很明确：先不继续做邮箱验证码、手机号验证这类扩展功能，优先把网站恢复到公网可以打开、后端接口可用、登录页体验正常的状态。

最终结果：

- SmartMall AI 首页恢复访问：[https://43fecc741649469ab11bd467c5f0cf3b.region1.waas.aigate.cc/](https://43fecc741649469ab11bd467c5f0cf3b.region1.waas.aigate.cc/)
- `/api/health` 返回 `200 OK`，后端状态为 `UP`。
- 登录页不再默认带 `demo / demo123456`。
- Waas 服务器上 Nginx 正常监听 `18081`，Spring Boot 后端监听 `18080`。
- 部署脚本可以完成数据库初始化、migration 执行、后端启动、Nginx 配置和健康检查。

## 一开始的现象

外部访问 SmartMall AI 时，首页、登录页和健康接口都返回：

```txt
502 Bad Gateway
openresty
Powered by APISIX
```

这个返回不是 Vue 页面自己的错误，也不是 Spring Boot 返回的业务错误，而是平台网关层没有成功转发到服务器内部服务。换句话说，请求还没有真正打到我们的 Nginx 或后端应用。

当时重点检查了三个地址：

```txt
/
/login
/api/health
```

三者全部是 502，说明问题不是某一个前端路由或某一个接口坏了，而是整条公网访问链路没有接通。

## 端口链路重新梳理

Waas 平台要求 HTTP 服务端口选择 `1024 - 65535`。之前部署脚本和 Nginx 配置里仍然带着传统服务器常用的 `80` 端口习惯，但平台暴露端口不能直接选 80，这就很容易造成外部网关转发端口和服务器内部监听端口不一致。

最终统一成下面这条链路：

```txt
浏览器
  -> Waas 公网 HTTPS 地址
  -> Waas HTTP 端口映射 18081
  -> Nginx 监听 18081
  -> Vue 静态资源
  -> /api 反向代理
  -> Spring Boot 监听 18080
  -> MySQL / Redis
```

对应修复包括：

- Waas 部署脚本默认 `PUBLIC_HTTP_PORT=18081`。
- Waas 专用 Nginx 配置改为监听 `18081`。
- Dockerfile Waas 版本暴露端口改为 `18081`。
- 后端内部端口使用 `18080`。
- Nginx 将 `/api/` 代理到 `127.0.0.1:18080`。

这样前端页面和后端接口都通过同一个公网域名访问，用户不需要感知后端端口。

## 登录页默认账号清理

线上登录页还有一个细节问题：进入登录页时，用户名和密码输入框默认带着 `demo / demo123456`。这在开发阶段方便测试，但放到公网展示就很不专业，也容易让人误解系统真的把账号密码硬编码在页面上。

这次把登录页做了清理：

- 表单初始值改为空。
- 切换登录/注册模式时不再回填演示账号。
- 表单增加 `autocomplete="off"`。
- 用户名和密码输入框使用独立的 `name`，减少浏览器自动填充旧账号的概率。
- 页面加载后再次执行一次清空，避免旧的浏览器密码管理器把演示账号塞回去。

这不是安全体系的全部，但至少让公网入口更像正式系统。真正的密码安全仍然应该依赖：

```txt
HTTPS 传输
后端 bcrypt / Argon2 哈希存储
数据库不保存明文密码
登录失败限流和权限校验
```

## 数据库迁移第一次中断

重新部署时，脚本一开始卡在第一个 migration：

```txt
ERROR 1064 ... ADD COLUMN IF NOT EXISTS role ...
```

原因是服务器上的 MySQL 版本不支持这种写法：

```sql
ALTER TABLE mall_user
  ADD COLUMN IF NOT EXISTS role ...
```

本地或部分新版本 MySQL 可以支持某些 `IF NOT EXISTS` 写法，但线上环境不能假设版本完全一致。为了解决这个问题，把 migration 改成了兼容写法：先查 `information_schema.columns`，判断字段是否存在，再动态执行 `ALTER TABLE`。

简化后的思路是：

```sql
SELECT COUNT(*)
FROM information_schema.columns
WHERE table_schema = DATABASE()
  AND table_name = 'mall_user'
  AND column_name = 'role';
```

如果不存在，再执行添加字段。这样即使脚本重复部署，也不会因为字段已经存在而失败。

## 数据库迁移第二次中断

继续部署时，又卡在评论和收藏数据：

```txt
Cannot add or update a child row: a foreign key constraint fails
```

这次原因是 migration 里插入了固定 `product_id` 的评论演示数据，例如 `product_id=28`、`product_id=9`、`product_id=3`。如果服务器当前数据库里的商品 ID 状态和本地不完全一致，就会触发外键失败。

这个问题的本质是：migration 不能盲目假设线上已有数据一定和本地一样。尤其是有外键约束的表，插入演示数据前必须确认父表数据存在。

修复方式是把固定插入改成：

```sql
INSERT INTO mall_product_review (...)
SELECT ...
FROM seed
JOIN mall_user u ON u.id = seed.user_id
JOIN mall_product p ON p.id = seed.product_id
ON DUPLICATE KEY UPDATE ...
```

这样只有用户和商品都存在时才会插入评论；如果商品不存在，就跳过这条种子数据，不会让整个部署中断。

收藏数据也采用同样方式处理。

## 数据库迁移第三次中断

修复外键后，又遇到一个 SQL 歧义问题：

```txt
Column 'created_at' in field list is ambiguous
```

原因是 `INSERT ... SELECT ... ON DUPLICATE KEY UPDATE created_at = created_at` 里，`created_at` 可能来自目标表，也可能来自查询结果，MySQL 不知道该用哪一个。

修复方式是明确指定目标表字段：

```sql
ON DUPLICATE KEY UPDATE
  created_at = mall_product_favorite.created_at;
```

这个问题提醒我，线上 migration 不能只看“本地能跑”，还要考虑 SQL 在不同上下文里的解析细节。部署脚本一旦自动化，就必须尽量减少这种隐式写法。

## 部署脚本增强

这次也顺手把 Waas 部署脚本做了一轮增强。脚本现在会做这些事情：

1. 解包最新发布包。
2. 准备 MySQL 数据库和账号。
3. 执行 `db/init/01_schema.sql`。
4. 按顺序执行 `db/migration/*.sql`。
5. 如商品表为空，再执行种子数据。
6. 启动 Redis。
7. 停掉旧的 Spring Boot 进程，启动新的后端 jar。
8. 等待 `/api/health` 返回成功。
9. 拷贝前端 `dist` 到 Nginx 静态目录。
10. 生成 Nginx 配置，监听 `18081`。
11. 重载 Nginx。
12. 验证后端健康检查和商品接口。

这样以后部署不会只停留在“文件传上去了”，而是脚本自己确认服务真的启动了。

## 三重缓存架构优化

除了把网站恢复上线，这一轮还继续推进了 SmartMall AI 的缓存架构。商城系统里商品列表、商品详情、首页推荐、个性化推荐都属于高频读接口，如果每次都直接查 MySQL，数据量和并发上来以后数据库压力会很大。

所以当前设计不是单纯“查数据库”，而是按三层读取：

```txt
L1：Caffeine 本地缓存
  -> 进程内缓存，速度最快，适合挡住短时间内的重复热点请求

L2：Redis 分布式缓存
  -> 多进程、多实例之间共享，适合部署扩展后的跨实例命中

L3：MySQL 数据库兜底
  -> 缓存未命中时读取真实数据，再回写 Redis 和本地缓存
```

这条链路的目标是让大部分重复读取停留在本地缓存或 Redis，只有第一次请求、缓存过期、主动失效后才访问数据库。

当前已经接入缓存的读链路包括：

- 商品分类。
- 商品列表。
- 商品详情。
- 首页推荐商品。
- 用户个性化推荐。
- 推荐缓存统计接口。

缓存失效也做了对应处理：

- 管理员修改商品后，清理商品详情、商品列表、首页推荐和用户推荐相关缓存。
- 下单成功后，库存和销量变化会触发商品详情、商品列表和首页推荐缓存失效。
- 用户产生浏览、收藏、加购、评价、购买等行为后，清理该用户的个性化推荐缓存。

缓存统计接口 `/api/cache/catalog/stats` 会返回本地命中、Redis 命中、缓存未命中、写入次数、清理次数、总读取次数和命中率。这个接口很重要，因为缓存不能只靠感觉判断有效，必须能量化命中情况。

这次优化后的缓存链路可以概括为：

```txt
请求进来
  -> 先查 Caffeine 本地缓存
  -> 本地没有再查 Redis
  -> Redis 没有再查 MySQL
  -> MySQL 查到后写回 Redis
  -> 同时写入本地缓存
  -> 返回结果
```

从工程角度看，这个架构后续也可以继续扩展，例如加入热点 key 预热、缓存空值防穿透、互斥锁防击穿、异步刷新、防止大 key 等策略。

这次压测带来的结论是：

- 三层缓存对重复读非常有效，特别是商品和推荐场景。
- 个性化推荐在 50 万行为记录下仍然可以通过缓存保持稳定读取。
- 大商品列表的瓶颈会从数据库转移到响应体大小和分页设计。
- 后续必须给 `GET /api/products` 增加分页参数，例如 `page`、`pageSize`、`total`。
- 缓存、索引、分页要一起设计，单独堆缓存不能解决所有性能问题。

## 这次踩坑的关键点

这次排障最有价值的地方，是把“网页打不开”拆成了多个可验证的小问题：

- 外部网关是否能访问？
- Waas 端口是否映射到了正确端口？
- 服务器内部是否真的监听 `18081`？
- Nginx 是否启动？
- Nginx 是否能访问前端静态文件？
- `/api` 是否能转发到后端？
- Spring Boot 是否监听 `18080`？
- 后端是否能连接 MySQL 和 Redis？
- 数据库 migration 是否完整执行？
- 登录页是否仍有开发阶段遗留默认账号？

如果只盯着浏览器里的一句 502，很容易乱猜；把链路拆开之后，每一步都可以用命令验证，问题就会逐渐收敛。

## 学到的东西

第一，部署脚本必须适配真实服务器环境。本地能跑的 SQL、端口、路径、进程管理方式，到了服务器上都可能不一样。

第二，migration 要尽量幂等。线上数据库不是空白库，部署脚本可能重复执行，所以字段、索引、种子数据都要考虑“已经存在”的情况。

第三，演示数据不能依赖固定 ID。尤其是带外键的评论、收藏、订单明细等数据，应该先确认父表记录存在，再插入子表。

第四，502 要从网关层开始查。它不一定是后端代码坏了，很多时候是端口没监听、Nginx 没启动、平台映射没对上。

第五，公网展示项目时，开发阶段的小方便会变成不专业的细节。比如默认账号密码、调试验证码、明文提示、测试数据乱码，都应该逐步清掉。
