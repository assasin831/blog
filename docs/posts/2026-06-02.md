# 6.2 学习：SmartMall AI 商品分页、接口兼容与压测链路继续优化

6.1 的复盘里已经把 SmartMall AI 的线上访问、三重缓存和压测结果梳理了一遍。当时压测暴露出一个很典型的问题：商品接口不是单纯查库慢，而是 `GET /api/products` 一次性把大量商品都返回给前端，响应体过大，前端渲染和网络传输都会变重。

所以 6.2 的重点不是继续盲目加缓存，而是把 6.1 写下来的后续计划往前推进一步：先给商品货架做分页，让接口返回“当前页数据 + 总量信息”，后续再围绕分页、索引、缓存和压测继续做优化。

![SmartMall AI 商品货架](/images/smartmall/products-phone.png)

## 今天做了什么

今天主要围绕商品列表分页做了四件事：

1. 后端给商品列表新增分页返回结构。
2. 前端商品货架接入页码、总数和分页按钮。
3. 缓存 key 纳入 `page/pageSize`，避免不同分页结果互相污染。
4. 压测脚本改为请求分页接口，后续测试更接近真实优化目标。

这次改动是向商业级电商系统靠近的一步。真实商城不可能一次把全部商品返回给浏览器，商品货架、搜索结果页、分类页都应该天然带分页或者游标。

## 后端分页设计

原来的接口是：

```http
GET /api/products
```

返回结构是商品数组。为了兼容首页、AI 助手和已有旧调用，这次没有直接破坏旧接口，而是做成兼容模式：

```http
GET /api/products
```

仍然返回旧数组。

```http
GET /api/products?page=1&pageSize=24
```

返回分页对象：

```json
{
  "items": [],
  "total": 50510,
  "page": 1,
  "pageSize": 24,
  "totalPages": 2105,
  "hasPrevious": false,
  "hasNext": true
}
```

这样做的好处是：

- 老接口不受影响，减少联调风险。
- 新页面可以拿到真实总数和总页数。
- 后续压测可以明确区分“一次性全量返回”和“分页返回”。

实现上新增了一个通用 `PageResponse<T>`，商品接口传入 `page/pageSize` 时走分页查询；没有传分页参数时继续走原来的列表逻辑。

## 查询和缓存调整

6.1 已经给商品查询做了 MySQL 索引和三重缓存：

```text
浏览器请求
  -> 后端接口
  -> Caffeine 本地缓存
  -> Redis 分布式缓存
  -> MySQL
```

分页以后缓存 key 也必须跟着变化。如果只按 `categoryId + keyword` 缓存，那么第一页、第二页、不同 pageSize 的数据可能混在一起。因此今天新增了分页维度：

```text
categoryId + keyword + page + pageSize
```

这使得：

- 首页第一页和第二页可以分别缓存。
- 不同分类页不会互相覆盖。
- 搜索关键词和分页参数能形成独立缓存。
- 管理员修改商品或订单改变库存销量时，仍然可以通过列表前缀统一失效。

## 前端商品货架变化

前端商品页之前只知道当前拿到多少商品，因此标题里显示的是当前数组长度。分页后，这个数字要变成后端返回的真实总量。

商品货架现在维护这些状态：

```text
page       当前页
pageSize   每页数量
total      商品总数
totalPages 总页数
items      当前页商品
```

页面底部增加了上一页、页码和下一页按钮。筛选分类或搜索关键词时会自动回到第一页，翻页时把 `page` 写进 URL query。这样刷新页面后仍然能停留在当前页，体验更像真实电商平台。

## 验证结果

后端编译通过：

```bash
mvn -DskipTests package
```

前端构建通过：

```bash
npm run build
```

本地启动后端后，请求分页接口：

```http
GET /api/products?page=1&pageSize=24
```

返回结果验证：

```text
itemCount: 24
total: 50510
page: 1
pageSize: 24
totalPages: 2105
```

分类分页接口：

```http
GET /api/products?categoryId=1&page=2&pageSize=12
```

返回结果验证：

```text
itemCount: 12
total: 4216
page: 2
pageSize: 12
totalPages: 352
```

旧接口兼容性也验证了：

```http
GET /api/products?categoryId=1
```

仍然返回数组，不会影响原有旧调用。

## 小规模压测

为了确认优化链路没有破坏接口，今天把 `scripts/load-test.mjs` 的 catalog 场景改成分页请求，然后跑了一轮小规模压测：

```text
scenario: catalog
total: 120
concurrency: 20
ok: 120
failed: 0
errorRate: 0
RPS: 1858.44
p50: 8.05 ms
p95: 19.91 ms
p99: 24.51 ms
```

这不是最终性能报告，但它说明分页改造后接口功能是稳定的，后续可以继续把并发规模加上去，再观察缓存命中率、数据库连接池、响应体大小和 MySQL 执行计划。

## 今天的收获

这次最大的收获是：性能优化不能只盯着“缓存命中率”。缓存很重要，但如果接口设计本身一次返回几万条数据，缓存也只是把大响应更快地吐出去，并没有从根上解决页面和网络负担。

分页是电商系统的基础能力，也是后续优化的前提。只有先把数据返回规模控制住，后面做索引、缓存预热、搜索排序、推荐重算和高并发压测才更有意义。

## 下一步

SmartMall AI 后续继续推进：

1. 给商品接口补充更完整的服务端排序参数，例如销量、价格和智能排序。
2. 做一次分页前后响应体大小对比，记录更直观的优化数据。
3. 继续完善 Redis 缓存预热、缓存空值和热点 key 保护。
4. 把远端服务器上的版本同步到这次分页改造后的版本。
5. 继续扩展 JMeter 或脚本化压测报告，把结果沉淀成项目文档。
