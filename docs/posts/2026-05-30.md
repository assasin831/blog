## AI 导购 Agent 的重点优化

一开始 AI 助手最大的问题是“不像导购”。用户问“550 元左右的手机”，它能给一个回答；但下一句问“有没有更便宜一点的”，它没有真正理解“更便宜”是相对于上一轮 550 元手机，而是会重新推荐完全不相关或者价格更高的商品。

今天重点把 AI 助手从简单聊天改成更接近 Agent 的工作方式。

### 1. 先优化用户问题，再交给推荐链路

用户输入通常是口语化的，比如：

> 有没有 400 元左右的手机推荐一下？

系统不能只把这句话原样丢给模型，而是先改写成更适合检索和决策的提示词：

```text
目标品类：手机数码 / 手机
预算约束：400 元左右
排序偏好：优先现货、价格匹配、销量和推荐分靠前
回答要求：必须基于商品库，不要编造不存在的商品
```

这样做之后，后端可以先根据品类、预算、库存、销量、推荐分去查商品，再让 AI 组织导购话术。也就是说，AI 不再是凭空回答，而是基于商品数据做解释。

### 2. 加入 Q / K / V 式对话记忆

为了处理多轮对话，我把对话上下文拆成类似 Q / K / V 的结构来理解：

| 记忆部分 | 在商城导购里的含义 | 示例 |
| --- | --- | --- |
| Q | 用户当前问题 | “有没有更便宜一点的手机？” |
| K | 用来检索历史意图的关键词 | 手机、预算 400、上一轮推荐商品、价格约束 |
| V | 上一轮可复用的结论 | 上一轮推荐了 Nova Mini 4G，价格 399 元 |

这样当用户追问“更便宜一点”时，系统不会把它当成一个孤立问题，而是会带着上一轮的品类和价格继续筛选。

### 3. 明确“比当前商品更便宜”的严格边界

这一点非常关键。用户说“有没有比这个手机更便宜的”，意思是：

- 品类仍然是手机。
- 价格必须低于上一轮推荐的手机价格。
- 不能推荐电脑、食品、车载用品。
- 不能推荐比上一轮更贵的手机。
- 如果商品库里没有更便宜的手机，应该直接说没有，而不是硬凑商品。

这让 AI 助手开始遵守电商导购的基本规则：推荐必须可解释、可购买、可落到商品库。

### 4. 增加品牌和品类约束

之前用户问“有没有苹果牌子的电脑推荐一下”，系统会推荐 Nimbus 办公笔记本，因为它只识别到了“电脑办公”，没有识别“苹果”这个品牌约束。

优化后的思路是：

1. 先提取品牌约束：苹果 / Apple。
2. 再提取品类约束：电脑 / 笔记本。
3. 到商品库里检索品牌与品类都匹配的商品。
4. 如果商品库没有这个品牌，明确告诉用户“当前商品库暂无苹果电脑”，并提示可选的相近品类或品牌。

这一步让 AI 从“会聊天”往“会查库、会判断、会拒绝错误推荐”靠近。

### 5. 身份问题不再胡乱回答

用户问“你是谁？”时，AI 不应该继续推荐商品，也不应该编造自己是某个外部大模型。它应该回答：

> 我是 SmartMall AI 的商城导购助手，可以根据预算、品类、用途、送礼对象和偏好，帮你筛选当前商城中真实存在的商品。

这个细节虽然小，但它能让产品感更稳定。

## 界面优化记录

今天对 UI 的判断标准从“能用”升级成“像真实电商平台一样自然”。

前台参考了京东、淘宝、亚马逊的常见结构：

- 顶部保持搜索框、导航、购物车、余额和用户入口，降低用户寻找成本。
- 首页加入左侧类目、热卖榜、促销区、猜你喜欢，让用户一进来就知道可以逛什么。
- 商品卡片保留价格、销量、库存、服务标签和加购按钮，信息密度更接近真实货架。
- 商品详情页加入规格、收藏、联系客服、评价晒单、库存和服务保障。
- 购物车支持收货人、手机号、地址、合计金额、余额支付和提交订单。
- 客服模块放在商品详情页右侧，用户可以围绕具体商品咨询价格、库存、配送和售后。

AI 助手页面也做了变化：

- 对话框里直接展示推荐商品卡片。
- 每个商品卡片可以直接查看详情或加入购物车。
- 右侧保留“导购建议”，显示本轮判断、购买提醒和可继续追问的问题。
- Agent 的工作流不再堆技术名词，而是用导购用户能理解的方式展示筛选结果。

## 数据库与三层架构思想

这个项目后面要继续往商业级系统靠，所以数据库不能只停留在“建几张表能查出来”的程度。今天梳理了一个更适合后续扩展的三层数据架构思想。

### 第一层：业务数据层

这一层是 MySQL 的核心业务表，负责保证数据真实、可靠、可追踪。

主要包括：

- 用户表：账号、昵称、手机号、角色、状态、余额。
- 商品表：分类、名称、价格、库存、销量、推荐分、主图、详情。
- 分类表：商品类目和导航结构。
- 购物车表：用户加购的商品和数量。
- 订单表与订单明细表：收货信息、支付金额、订单状态、商品快照。
- 收藏表：用户收藏商品。
- 评论表：评分、评价内容、点赞数、创建时间。
- 客服会话表：用户与管理员客服的对话。
- 钱包流水表：充值、支付、退款等余额变动。
- 用户行为表：浏览、收藏、加购、评价、购买等行为记录。
- Agent 记忆表：多轮对话摘要、最近推荐商品、用户偏好。

### 第二层：查询与索引层

这一层解决“查得快、查得准”的问题。

电商系统高频查询非常集中：

- 首页推荐商品。
- 商品列表分页。
- 按分类筛选。
- 按关键词搜索。
- 按价格、销量、推荐分排序。
- 用户订单列表。
- 用户收藏列表。
- 商品详情与评论。
- 管理端按状态查订单和商品。

所以后续需要重点设计索引：

| 场景 | 可能的索引方向 |
| --- | --- |
| 商品货架 | category_id、status、price、sales、recommend_score |
| 搜索排序 | name、subtitle、category_id、status、recommend_score |
| 用户订单 | user_id、status、created_at |
| 用户行为 | user_id、product_id、action_type、created_at |
| 钱包流水 | user_id、type、created_at |
| 评论列表 | product_id、rating、created_at |

今天已经先在代码层修复搜索相关性，后续会继续把索引和 SQL 执行计划一起调优。

### 第三层：缓存与推荐层

这一层是后续 Redis 多级缓存和推荐算法的落点。

初期先使用本地缓存和后端内存结构验证逻辑，后面计划升级为：

- 本地缓存：缓存短时间内重复读取的分类、热点商品和配置。
- Redis 缓存：缓存商品详情、首页推荐、热卖榜、用户推荐候选集。
- 数据库兜底：缓存未命中时回源 MySQL。
- 行为分值：根据点击、收藏、加购、评价、购买计算用户偏好。
- 协同过滤：用相似用户和相似商品补充推荐。

用户行为分值的初步思路是：

| 行为 | 含义 | 推荐权重 |
| --- | --- | --- |
| 浏览 | 用户有轻度兴趣 | 低 |
| 收藏 | 用户有明确兴趣 | 中 |
| 加购 | 用户有购买意向 | 高 |
| 评价 | 用户已深度使用 | 中高 |
| 购买 | 用户真实成交 | 最高 |

这样首页“猜你喜欢”就不只是按销量排序，而是结合用户自己的行为偏好生成。

## 高并发与性能方向

商业级商城一定会遇到并发问题。今天也开始把后续压测方向列出来：

- 使用 JMeter 或类似工具模拟上千并发请求。
- 分别压测商品列表、商品详情、搜索、加购、下单、AI 导购接口。
- 观察 QPS、平均响应时间、P95、P99、错误率和数据库连接池状态。
- 对热点商品详情和首页推荐加缓存。
- 对库存扣减、订单创建、余额支付做幂等设计。
- 对 AI 导购接口设置超时、降级和本地推荐兜底。

AI 接口尤其需要降级，因为模型响应天然比普通接口慢。后续要把“商品筛选”和“导购话术生成”拆开：筛选必须快，话术可以慢一点；如果模型超时，也能先返回可购买的商品结果。

## 博客搭建与发布

晚上开始把项目过程放进个人博客。

博客技术选型是 VitePress：

- 用 Markdown 写每日记录和项目复盘。
- 用 VitePress 生成静态页面。
- 用 GitHub Actions 自动构建。
- 用 GitHub Pages 发布到线上。

部署过程中遇到的主要问题是 GitHub Pages 项目站点的路径不是根路径，而是 `/blog/`。如果链接写成 `/posts/2026-05-30`，线上会跳到 `assasin831.github.io/posts/2026-05-30`，自然就是 404。

最后修复思路是：

- VitePress 配置 `base: '/blog/'`。
- 自定义 HTML 链接使用 `/blog/...`。
- VitePress 内部导航保持框架能识别的链接。
- 构建后检查关键页面是否能返回 200。

## 今天学到的东西

今天最大的体会是，项目越往后做，越不能只盯着一个功能点。

一个商城系统背后至少有几条线同时推进：

- 用户线：用户能不能自然完成浏览、咨询、收藏、加购、支付、评价。
- 管理员线：运营人员能不能管理商品、订单、用户和客服消息。
- 数据线：用户行为有没有被记录，能不能反过来支持推荐。
- AI 线：模型有没有被约束在真实商品库内，能不能处理多轮追问。
- 性能线：热点数据、数据库索引、缓存、降级和压测是不是有规划。
- 发布线：代码能不能构建、上线、回滚和持续记录。
